This article introduces authentication and access control in Databricks. For information about securing access to your data, see [Data governance with Unity Catalog](/aws/en/data-governance/).

## Identity provider setup

In the Databricks account console, identity provider configuration lives on a single **Identity provider setup** page. As an account admin, go to **Security** > **Identity provider setup** to manage how users sign in and how identities sync to your account.

The page organizes these controls into the following sections:

* **Authentication**: Configure your sign-in method, such as single sign-on (SSO) with your identity provider, and set your multi-factor authentication (MFA) policy.
* **Identity management**: Manage how users and groups are provisioned to your account, including automatic identity management, SSO just-in-time (JIT) provisioning, and SCIM user provisioning. For eligible or preview accounts, this section also includes identity attributes and the domain access list.
* **Federation policies**: Create policies that let workloads authenticate to Databricks using tokens issued by your identity provider.
* **Unified login**: Apply a single SSO configuration across your account and all Databricks workspaces.

* **Emergency access**: Designate users who can sign in with a password and multi-factor authentication to prevent lockouts.

## Sign in to Databricks

Databricks recommends configuring single sign-on (SSO) and unified login for greater security and improved usability. SSO enables your users to sign in to Databricks using your organization's identity provider.

For most accounts, unified login is enabled by default. This means that a single SSO configuration is used across your account and all Databricks workspaces. Once SSO is configured, you can enable fine-grained access control, such as multi-factor authentication, using your identity provider. See [Configure SSO in Databricks](/aws/en/security/auth/single-sign-on/).

When SSO is configured, you can configure just-in-time (JIT) provisioning to automatically create new user accounts from your identity provider upon their first login. See [Automatically provision users (JIT)](/aws/en/security/auth/jit).

If you don't configure single sign-on, users can login to Databricks using a selected external account, like Google, or a one-time passcode. See [Sign-in with email or external accounts](/aws/en/security/auth/email-login).

To prevent lockouts, account admins can set up emergency access for up to 20 users. These users can sign into Databricks using a password and multi-factor authentication. See [Emergency access to prevent lockouts](/aws/en/security/auth/single-sign-on/emergency-access).

## Sync users and groups from your identity provider

You can sync users and groups automatically from your identity provider to your Databricks account using automatic identity management or SCIM. Using automatic identity management, you can directly search in identity federated workspaces for users, service principals, and groups in your identity provider and add them to your workspace and to the Databricks account. Databricks uses your identity provider as the source of record, so any changes to users or group memberships are respected in Databricks. For detailed instructions, see [Automatic identity management](/aws/en/admin/users-groups/automatic-identity-management/).

You can also use SCIM provisioning to sync users and groups from your identity provider to Databricks, see [Sync users and groups from your identity provider using SCIM](/aws/en/admin/users-groups/scim/).

For more information on how to best configure users and groups in Databricks, see [Identity best practices](/aws/en/admin/users-groups/best-practices).

## Secure API authentication with OAuth

Databricks OAuth supports secure credentials and access for resources and operations at the Databricks workspace level and supports fine-grained permissions for authorization.

Databricks also supports personal access tokens (PATs), but recommends you use OAuth instead. To monitor and manage PATs, see [Monitor and revoke personal access tokens](/aws/en/admin/access-control/tokens) and [Manage personal access token permissions](/aws/en/security/auth/api-access-permissions).

To reduce the need for long-lived service principal secrets, a user who manages a service principal can act as it using OAuth on-behalf-of (OBO), which uses the interactive user-to-machine (U2M) OAuth flow. See [Authenticate as a service principal using OAuth OBO](/aws/en/dev-tools/auth/oauth-m2m#oauth-obo).

See [Authorize access to Databricks resources](/aws/en/dev-tools/auth/).

## Access control overview

In Databricks, there are different access control systems for different securable objects. The table below shows which access control system governs which type of securable object.

| Securable object | Access control system |
| --- | --- |
| Workspace-level securable objects | Access control lists |
| Account-level securable objects | Account role based access control |
| Data securable objects | Unity Catalog |

Databricks also provides admin roles and entitlements that are assigned directly to users, service principals, and groups.

For information about securing data, see [Data governance with Unity Catalog](/aws/en/data-governance/).

### Access control lists

In Databricks, you can use access control lists (ACLs) to configure permission to access workspace objects such as notebooks and SQL Warehouses. All workspace admin users can manage access control lists, as can users who have been given delegated permissions to manage access control lists. For more information on access control lists, see [Access control lists](/aws/en/security/auth/access-control/).

### Account role based access control

You can use account role based access control to configure permission to use account-level objects such as service principals and groups. Account roles are defined once, in your account, and apply across all workspaces. All account admin users can manage account roles, as can users who have been given delegated permissions to manage them, such as group managers and service principal managers.

Follow these articles for more information on account roles on specific account-level objects:

* [Roles for managing service principals](/aws/en/security/auth/access-control/service-principal-acl)
* [Manage permissions on a group](/aws/en/admin/users-groups/manage-groups#manage-group-roles-account)

### Admin roles and workspace entitlements

There are two main levels of admin privileges available on the Databricks platform:

* Account admins: Manage the Databricks account, including workspace creation, user management, cloud resources, and account usage monitoring.

* Workspace admins: Manage workspace identities, access control, settings, and features for individual workspaces in the account.

There are also feature-specific admin roles with a narrower set of privileges. To learn about the available roles, see [Databricks administration overview](/aws/en/admin/admin-concepts).

An entitlement is a property that allows a user, service principal, or group to interact with Databricks in a specified way. Workspace admins assign entitlements to users, service principals, and groups at the workspace-level. For more information, see [Manage entitlements](/aws/en/security/auth/entitlements).
