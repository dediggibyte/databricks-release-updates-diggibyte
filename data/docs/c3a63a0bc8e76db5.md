## Overview

A PostgreSQL integrated change data capture (CDC) pipeline ingests change data from a PostgreSQL source into Databricks using a single pipeline.

Unlike the standard gateway-based architecture, which requires a separate ingestion gateway and ingestion pipeline, an integrated CDC pipeline runs both extraction and application stages in one pipeline update.

Key benefits over the two-pipeline approach:

* Simpler setup: one pipeline instead of two.
* Less operational overhead: no separate long-running gateway process to manage.
* Auto full refresh: If you configure an auto full refresh policy, the pipeline runs a full refresh automatically when a table needs one, instead of waiting for you to run it.

## Architecture comparison: integrated vs. gateway-based

| Feature | Gateway-based (standard) | Integrated CDC |
| --- | --- | --- |
| Number of pipelines | Two (ingestion gateway + ingestion pipeline) | One (unified pipeline) |
| Setup complexity | Create a gateway, then create an ingestion pipeline referencing the gateway ID | Create a single pipeline with a Unity Catalog connection |
| Gateway mode | Gateway runs continuously as a separate long-running process | Extraction is embedded in the pipeline |
| Connection reference | `ingestion_gateway_id` | `connection_name` |
| Connector type | Implicit default CDC behavior | Explicit: `connector_type: CDC` |
| Staging volume | Managed internally by gateway | Auto-created in the destination schema or configured through `data_staging_options` |
| Pipeline mode | Continuous | Continuous (default) and triggered |
| Compute | Classic for the gateway, serverless for the managed ingestion pipeline | Classic or serverless |
| Auto full refresh | Not supported for the existing PostgreSQL gateway-based flow | Supported |

Both architectures support API-based and UI-based pipeline authoring, incremental ingestion, Unity Catalog governance, and a maximum of 250 tables per pipeline.

## How an integrated CDC pipeline runs

Each pipeline update runs two stages in sequence:

1. **Extraction**: The pipeline connects to the source database using the Unity Catalog connection. On the first run or a full refresh, it captures an initial snapshot. On subsequent runs, it captures incremental changes (inserts, updates, and deletes) using PostgreSQL logical replication through a replication slot with the pgoutput plugin. The pipeline writes extracted data to a Unity Catalog staging volume.
2. **Application**: The pipeline reads from the staging volume and applies changes to destination streaming tables in Unity Catalog. Merge operations use the configured primary keys and slowly changing dimension (SCD) type. The pipeline is designed to provide exactly-once semantics.

## Requirements

To create an integrated CDC pipeline, you must meet the following requirements:

* Your workspace is enabled for Unity Catalog.
* If you plan to create a connection: You have `CREATE CONNECTION` privileges on the metastore. See [Manage privileges in Unity Catalog](/aws/en/data-governance/unity-catalog/manage-privileges/).

  If your connector supports UI-based pipeline authoring, you can create the connection and the pipeline at the same time by completing the steps on this page. However, if you use API-based pipeline authoring, you must create the connection in Catalog Explorer before you complete the steps on this page. See [Connect to managed ingestion sources](/aws/en/connect/managed-ingestion).
* If you plan to use an existing connection: You have `USE CONNECTION` privileges or `ALL PRIVILEGES` on the connection.
* You have `USE CATALOG` privileges on the target catalog.
* You have `USE SCHEMA`, `CREATE TABLE`, and `CREATE VOLUME` privileges on an existing schema or `CREATE SCHEMA` privileges on the target catalog.

* You have access to a primary PostgreSQL instance. Logical replication is only supported on primary instances and not on read replicas.
* To ingest from PostgreSQL, you must also complete the [source setup](/aws/en/ingestion/lakeflow-connect/postgresql-source-setup).

### Compute requirements

An integrated CDC pipeline runs on classic or serverless compute:

* **Classic compute**: The classic compute plane runs in your Databricks workspace virtual private cloud (VPC) or VNet and must reach your PostgreSQL instance over the network. Supported network paths include VPC or VNet peering, public endpoints, and, for on-premises PostgreSQL, VPN.

  For on-premises PostgreSQL, you can also use AWS Direct Connect.
* **Serverless compute**: Configure [serverless network connectivity](/aws/en/security/network/serverless-network-security/) between Databricks serverless compute and your source database. On-premises sources require a network path through the configured serverless egress (for example, a transit gateway or VPN).

For classic compute, you can use unrestricted cluster creation permissions or a custom [cluster policy](/aws/en/ldp/configure-compute#cluster-policy) with `cluster_type` fixed to `dlt`, `runtime_engine` fixed to `STANDARD`, and at least 8 cores recommended for efficient extraction.

## Create an integrated CDC pipeline

Create integrated CDC pipelines using the API, the Databricks CLI, notebooks, or Declarative Automation Bundles.

* Declarative Automation Bundles
* Databricks notebook
* Databricks CLI
* REST API

Define the pipeline resource in a bundle file (for example, `resources/integrated_cdc_pipeline.yml`):

YAML

```
variables:

pipeline_name:

description: 'Name for the integrated CDC pipeline'

connection_name:

description: 'Unity Catalog connection name'

dest_catalog:

description: 'Destination catalog for ingested data'

dest_schema:

description: 'Destination schema for ingested data'

resources:

pipelines:

integrated_cdc_pipeline:

name: ${var.pipeline_name}

catalog: ${var.dest_catalog}

schema: ${var.dest_schema}

# Pipeline mode: true runs in continuous mode (the default if omitted).

# Set to false to run in triggered mode, and schedule the pipeline with a job.

continuous: true

ingestion_definition:

connection_name: ${var.connection_name}

connector_type: CDC

objects:

- table:

source_catalog: 'my_database'

source_schema: 'public'

source_table: 'customers'

destination_catalog: ${var.dest_catalog}

destination_schema: ${var.dest_schema}

destination_table: 'customers'

table_configuration:

scd_type: 'SCD_TYPE_1'
```

If you enable triggered mode (`continuous: false`), set up a job like the following to run the pipeline on a schedule (for example, `resources/integrated_cdc_job.yml`). Because each triggered update runs for up to approximately 30 minutes, an interval of 60 minutes is a good starting point:

YAML

```
resources:

jobs:

integrated_cdc_job:

name: '${var.pipeline_name}-job'

tasks:

- task_key: 'cdc_ingestion'

pipeline_task:

pipeline_id: ${resources.pipelines.integrated_cdc_pipeline.id}

schedule:

quartz_cron_expression: '0 0 * * * ?'

timezone_id: 'UTC'
```

Deploy the bundle with the Databricks CLI:

Shell

```
databricks bundle deploy

# Continuous mode (default): start the pipeline

databricks bundle run integrated_cdc_pipeline

# Triggered mode (continuous: false): run the scheduled job

databricks bundle run integrated_cdc_job
```

For more information, see [What are Declarative Automation Bundles?](/aws/en/dev-tools/bundles/).

The following example creates a pipeline in continuous mode. Set `continuous` to `False` for triggered mode.

Python

```
from databricks.sdk import WorkspaceClient

from databricks.sdk.service.pipelines import (

ConnectorType,

IngestionConfig,

IngestionPipelineDefinition,

TableSpec,

)

w = WorkspaceClient()

pipeline = w.pipelines.create(

name="<pipeline-name>",

catalog="<destination-catalog>",

schema="<destination-schema>",

continuous=True,  # Set to False to run in triggered mode.

ingestion_definition=IngestionPipelineDefinition(

connection_name="<unity-catalog-connection-name>",

connector_type=ConnectorType.CDC,

objects=[

IngestionConfig(

table=TableSpec(

source_catalog="<source-database>",

source_schema="<source-schema>",

source_table="<source-table>",

destination_catalog="<destination-catalog>",

destination_schema="<destination-schema>",

)

)

],

),

)

print(f"Pipeline created: {pipeline.pipeline_id}")
```

## Operational safeguards

### Pipeline mode and scheduling

PostgreSQL integrated CDC pipelines run in continuous mode by default when `continuous` is not set. Continuous mode keeps the replication slot caught up with the source, which minimizes the risk of write-ahead log (WAL) bloat.

To run in triggered mode, set `continuous` to `false` and schedule the pipeline with a [Lakeflow Jobs](/aws/en/jobs/) task. Each triggered update stops after it catches up with the source (see [Smart closure for integrated CDC pipelines](/aws/en/ingestion/lakeflow-connect/smart-closure)). Each update runs for a maximum of approximately 30 minutes. A large backlog can span several updates, and each update resumes where the previous one stopped.

Schedule updates often enough for the pipeline to catch up and to prevent WAL accumulation on the source. A 60-minute interval is a good starting point for most workloads. If a trigger fires while an update is still running, the new update is queued.

### Replication slot health monitoring

Integrated CDC pipelines monitor the health of the replication slots they use and report their status every 5 minutes in the event log. You can also see slot health in the UI and query it from the event log.

The monitoring runs as part of the pipeline, so slot health metrics are emitted only while the pipeline is running.
