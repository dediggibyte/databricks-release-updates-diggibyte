## Pipeline settings

Pipeline settings fall into two categories:

* **Source code**: The collection of files that declare datasets using pipeline syntax. See [Configure source code](#source-code).
* **Infrastructure**: Settings that control compute, how updates are processed, and where tables are stored.

Most settings have reasonable defaults, but two require attention before running in production:

* **Target catalog and schema**: To make data available outside the pipeline, declare a target catalog and schema. Data is published to Unity Catalog by default. See [Set the target catalog and schema](/aws/en/ldp/target-schema).
* **Data access**: The compute used for execution must have permissions configured for your data sources and, if specified, a storage location.

## Configure a new pipeline

To configure a new pipeline, do the following:

1. At the top of the sidebar, click  **New** and then select  **ETL pipeline**.
2. At the top, give your pipeline a unique name.
3. Under the name, you can see the default catalog and schema that have been chosen for you. Change these to give your pipeline different defaults.

   The default [catalog](/aws/en/catalogs/) and the default [schema](/aws/en/schemas/) are where datasets are read from or written to when you do not qualify datasets with a catalog or schema in your code. See [Database objects in Databricks](/aws/en/database-objects/) for more information.
4. Select your preferred option to create a pipeline:

   * **Start with sample code in SQL** to create a new pipeline and folder structure, including sample code in SQL.
   * **Start with sample code in Python** to create a new pipeline and folder structure, including sample code in Python.
   * **Start with a single transformation** to create a new pipeline and folder structure, with a new blank code file.
   * **Add existing assets** to create a pipeline that you can associate with existing code files in your workspace.
   * **Create a source-controlled project** to create a pipeline with a new Declarative Automation Bundles project, or to add the pipeline to an existing bundle.

   You can have both SQL and Python source code files in your ETL pipeline. When creating a new pipeline and choosing a language for the sample code, the language is only for the sample code included in your pipeline by default.
5. When you make your selection, you are redirected to the newly created pipeline.

   The ETL pipeline is created with the following default settings:

   * [Unity Catalog](/aws/en/data-governance/unity-catalog/)
   * [Current channel](/aws/en/release-notes/dlt/#runtime-channels)
   * [Serverless compute](/aws/en/compute/serverless/)

   This configuration is recommended for many use cases, including development and testing, and is well-suited to production workloads that should run on a schedule. For details on scheduling pipelines, see [Pipeline task for jobs](/aws/en/jobs/tasks/pipeline).

   You can adjust these settings from the pipeline toolbar.

Alternatively, you can create an ETL pipeline from the workspace browser:

1. Click **Workspace** in the left side pane.
2. Select any folder, including Git folders.
3. Click **Create** in the upper-right corner, and click **ETL pipeline**.

You can also create an ETL pipeline from the jobs and pipelines page:

1. In your workspace, click  **Jobs & Pipelines** in the sidebar.
2. Under **New**, click **ETL Pipeline**.

## Compute configuration options

Databricks recommends always using **Enhanced autoscaling**. Default values for other compute configurations work well for many pipelines.

Serverless pipelines remove compute configuration options. For configuration instructions for serverless pipelines, see [Configure a serverless pipeline](/aws/en/ldp/serverless).

Use the following settings to customize compute configurations:

* Workspace admins can configure a **Cluster policy**. Compute policies allow admins to control what compute options are available to users. See [Select a compute policy](/aws/en/ldp/configure-compute#cluster-policy).
* You can optionally configure **Cluster mode** to run with **Fixed size** or **Legacy autoscaling**. See [Optimize Lakeflow pipeline cluster utilization with autoscaling](/aws/en/ldp/auto-scaling).
* For workloads with autoscaling enabled, set **Min workers** and **Max workers** to set limits for scaling behaviors. See [Configure classic compute for pipelines](/aws/en/ldp/configure-compute).
* You can optionally turn off Photon acceleration. See [What is Photon?](/aws/en/compute/photon).

* Select an **Instance profile** if your pipeline uses an instance profile to control access to cloud services. See [Cloud storage configuration](/aws/en/ldp/hive-metastore#configure-cloud-storage).

* Use **Cluster tags** to help monitor costs associated with pipelines. See [Configure compute tags](/aws/en/ldp/configure-compute#tags).
* Configure **Instance types** to specify the type of virtual machines used to run your pipeline. See [Select instance types to run a pipeline](/aws/en/ldp/configure-compute#instance-types).
  + Select a **Worker type** optimized for the workloads configured in your pipeline.
  + You can optionally select a **Driver type** that differs from your worker type. This can be useful for reducing costs in pipelines with large worker types and low driver compute utilization or for choosing a larger driver type to avoid out-of-memory issues in workloads with many small workers.

## Set the run-as user

Run-as user allows you to change the identity that a pipeline uses to run, and the ownership of the tables it creates or updates. This is useful in situations where the original user who created the pipeline has been deactivated, for example, if they left the company. In those cases, the pipeline can stop working, and the tables it published can become inaccessible to others. By updating the pipeline to run as a different identity, such as a service principal, and reassigning ownership of the published tables, you can restore access and ensure the pipeline continues to function. Running pipelines as service principals is considered a best practice because they are not tied to individual users, making them more secure, stable, and reliable for automated workloads.

### Required permissions

**For the user making the change:**

* **CAN\_MANAGE** permissions on the pipeline
* **CAN\_USE** role on the service principal (if setting run-as to a service principal)
* Membership in the group, or **Assume** permission on the group (if setting run-as to a group). See [Set the run-as identity to a group](#run-as-group).

**For the run-as user, service principal, or group:**

* **Workspace Access:**

  + **Workspace access** permission to operate within the workspace
  + **Can use** permission on cluster policies used by the pipeline
  + Compute creation permission in the workspace
* **Source Code Access:**

  + **Can read** permission on all notebooks included in the pipeline source code
  + **Can read** permission on workspace files if the pipeline uses them
* **Unity Catalog Permissions** (for pipelines using Unity Catalog):

  + `USE CATALOG` on the target catalog
  + `USE SCHEMA` and `CREATE TABLE` on the target schema
  + `MODIFY` permission on existing tables that the pipeline updates
  + `CREATE SCHEMA` permission if the pipeline creates new schemas
* **Legacy Hive metastore Permissions** (for pipelines using Hive metastore):

  + `SELECT` and `MODIFY` permissions on target databases and tables
* **Additional Cloud Storage Access** (if applicable):

  + Permissions to read from source storage locations
  + Permissions to write to target storage locations

### How to set the run-as user

You can set the `run-as` user through the pipeline settings from the pipeline monitoring page or the pipeline editor. To change the user from the pipeline monitoring page:

1. Click **Jobs & Pipelines** to open the list of pipelines, and select the name of the pipeline you wish to edit.
2. On the pipeline monitoring page, click **Settings**.
3. In the **Pipeline settings** sidebar, click  **Edit** next to **Run as**.
4. In the edit widget, select one of the following options:
   * Your own user account
   * A service principal for which you have **CAN\_USE** permission
   * An account group that you are a member of, or that you have **Assume** permission on. See [Set the run-as identity to a group](#run-as-group).
5. Click **Save** to apply the changes.

When you successfully update the run-as user:

* The pipeline identity changes to use the new user, service principal, or group for all future runs
* In Unity Catalog pipelines, the owner of tables published by the pipeline is updated to match the new run-as identity
* Future pipeline updates use the permissions and credentials of the new run-as identity
* Like any settings change, the new identity applies to the next pipeline update: continuous pipelines automatically restart with the new identity, while triggered pipelines apply it on their next run. The run-as change can interrupt an active update. See [How configuration changes take effect](#config-changes-take-effect).

note

If the update of run-as fails, you receive an error message explaining the reason for the failure. Common issues include insufficient permissions on the service principal.

### Set the run-as identity to a group

Setting a pipeline's **Run as** identity to an account group works the same way as setting it to a user or a service principal. Pipeline updates run with the group's permissions, and in Unity Catalog pipelines the tables the pipeline publishes are owned by the group. Use a group when you want a team to own an automated pipeline rather than tying it to one person's account, so the pipeline keeps working as team membership changes.

In Databricks, a role is implemented as a group, so a pipeline whose **Run as** is set to a group runs as that role. See [Role-based access control (RBAC)](/aws/en/security/auth/rbac/).

Setting **Run as** to a group does not change who owns the pipeline. Ownership and the run-as identity are separate settings. To change the owner, see [Change the pipeline owner](/aws/en/ldp/privileges#change-owner).

To configure **Run as** to a group, you must either:

* Be a member of the group, or
* Have **Assume** permission on the group, if the group is being used for [exclusive access](/aws/en/security/auth/rbac/exclusive-access).

The group must be an account group that is assigned to the workspace. Workspace-local groups cannot be used as a run-as identity, and neither can the broad built-in groups `admins`, `users`, and `account users`.

Grant the group every permission the pipeline needs, as listed in [Required permissions](#required-permissions). Because updates run as the group, granting yourself access to the pipeline's source code and data is not enough.

To set **Run as** to a group in the workspace UI, follow the steps in [How to set the run-as user](#how-to-set-the-run-as-user) and search for the group in the edit widget. Groups appear alongside users and service principals. To confirm the change, reopen the **Pipeline settings** sidebar and check that **Run as** shows the group.

To set a group as the run-as identity with the REST API, set `run_as.group_name` to the group's name. To create a pipeline that runs as a group, run the following:

JSON

```
{  
  "name": "sales-etl",  
  "run_as": {  
    "group_name": "Test Group"  
  }  
}
```

For the full request, see [Create a pipeline](https://docs.databricks.com/api/workspace/pipelines/create). When you update an existing pipeline definition, set `updated_run_as.group_name` instead.

To set a group as the run-as identity in a Declarative Automation Bundles bundle, set `group_name` in the pipeline resource's `run_as` mapping:

YAML

```
resources:  
  pipelines:  
    sales_etl:  
      name: sales-etl  
      run_as:  
        group_name: Test Group
```

A `SET OWNER TO` SQL statement cannot set a group as the owner of a materialized view or streaming table. Use the workspace UI for that. See [Use `ALTER` statements with pipeline datasets](/aws/en/ldp/using-alter-sql).

Jobs support the same run-as group configuration. See [Set Run as to a group](/aws/en/jobs/privileges#run-as-group).
