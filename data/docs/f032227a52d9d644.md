Beta

This feature is in [Beta](/aws/en/release-notes/release-types). To use it, a workspace admin must turn on **Unity Gateway skills in Genie** from the **Previews** page. See [Manage Databricks previews](/aws/en/admin/workspace-settings/manage-previews).

Create a skill with your coding agent, publish it to Unity Catalog, and share it with teammates. If you already manage skills in GitHub, [publish them with a GitHub Action](#publish-skills-from-your-github-repository). For upstream repositories where you cannot add a workflow, [sync them with a notebook](#sync-a-git-skill-repository-to-a-uc-schema). To create and manage skills with the REST API, the Databricks CLI, or the SDKs instead, see [Skills API and SDK reference](/aws/en/ai-gateway/skill-reference).

## Requirements

* A Unity Catalog-enabled Databricks workspace, and your workspace URL (for example, `https://my-company.cloud.databricks.com`). Creating and updating skills must be enabled for your workspace. Workspaces that use the [compliance security profile](/aws/en/security/privacy/security-profile) block these operations. See [Account and compliance considerations](/aws/en/ai-gateway/govern-skills#compliance).
* An existing schema in a standard Unity Catalog catalog with a [managed storage location](/aws/en/connect/unity-catalog/cloud-storage/managed-storage). See [Set up a governed schema for skills](/aws/en/ai-gateway/govern-skills#set-up-a-schema).
* `USE CATALOG` on the target catalog, and `USE SCHEMA` and `CREATE VOLUME` on the target schema. Your Databricks admin grants these. See [Govern skills](/aws/en/ai-gateway/govern-skills#grant-access) for the full model.

## Create and publish a skill interactively

To draft and publish a skill from your coding agent, install Python 3.12+ and [uv](https://docs.astral.sh/uv/), then follow these steps. You need a coding agent that supports the Model Context Protocol (MCP), the standard agents use to connect to tools. You can skip these CLI setup steps when publishing an existing skill from GitHub.

### Install and connect the Unity Gateway CLI

Install the [Unity Gateway CLI](https://github.com/databricks/unity-gateway) and use it to connect your coding agent to your Databricks workspace's skill registry.

The Unity Gateway CLI signs you in to your workspace and registers the *Databricks Skills MCP server* (`databricks-skill-registry`) that your agent uses to create and update skills.

prompt

Have your agent install and connect the Unity Gateway CLI for you:

```
Install the Unity Gateway CLI from its Git source and connect my coding agent to Databricks:

1. Run: uv tool install git+https://github.com/databricks/unity-gateway

2. Run: ug configure --agents <your-agent> --workspaces https://<workspace-host>

3. Run: ug skills

Use <your-agent> = my coding agent (claude, codex, gemini, opencode, or copilot) and

<workspace-host> = my workspace URL host (for example, my-company.cloud.databricks.com).

A browser will open during step 2 for me to sign in.
```

To do it yourself, run the same commands in your terminal:

Bash

```
uv tool install git+https://github.com/databricks/unity-gateway

ug configure --agents <your-agent> --workspaces https://<workspace-host>

ug skills
```

Replace `<your-agent>` with the name of the coding agent you use (for example, `claude`, `codex`, `gemini`, `opencode`, or `copilot`), and `<workspace-host>` with your workspace URL host. A browser opens during `ug configure` for you to sign in. Restart your agent afterward (`ug <your-agent>`) so it loads the new tools.

### Develop a skill locally

A skill is a folder: a `SKILL.md` file with instructions, plus any supporting files the agent should read. You can ask your coding agent or [Genie Code](/aws/en/genie-code/skills) to draft and refine these files. For a skill authored in Genie Code, download its folder locally, then publish it with the connected coding agent.

In this tutorial you build a `databricks-sql-guide` skill: your team's conventions for writing Databricks SQL, so every query an agent writes follows the same standards.

prompt

Have your agent draft the skill for you:

```
Draft a databricks-sql-guide skill in a local folder ./databricks-sql-guide. Create a SKILL.md

with our Databricks SQL conventions: snake_case naming, named CTEs over nested subqueries,

filter on partition columns, and avoid SELECT *. Give it a specific description that says what

it covers and when to use it.
```

The agent writes a folder like this:

```
databricks-sql-guide/

└── SKILL.md
```

A minimal `SKILL.md` has YAML frontmatter and instructions:

Markdown

```
---

name: databricks-sql-guide

description: Databricks SQL conventions for writing queries — use for any Databricks SQL authoring or review.

---

# Databricks SQL guide

- Use snake_case for table, column, and CTE names.

- Prefer named CTEs over nested subqueries.

- Always filter on partition columns when they exist.

- Never use `SELECT *`; list columns explicitly.
```

The `description` matters most: it is what agents match against when deciding whether to use a skill, so make it specific about *what* the skill covers and *when* to reach for it. Review the draft and refine it until it captures your conventions.

### Publish the skill to Unity Catalog

Publishing uploads your local folder to a Unity Catalog schema as a governed skill. You become the skill's **owner**, and it is private to you until you share it.

prompt

Have your agent publish it for you:

```
Publish my ./databricks-sql-guide folder to the acme.sql_skills schema in Databricks.
```

The agent calls the `create_skill` MCP tool to upload the folder and register the skill.

To change the skill later, edit the local folder and prompt the agent to update it from your folder. The agent calls `update_skill` on the same server.

## Share your skill

A published skill is private until you grant access. Skills that the [GitHub Action](#publish-skills-from-your-github-repository) creates are owned by its service principal. The skill owner or a principal with [`MANAGE`](/aws/en/data-governance/unity-catalog/access-control/privileges-reference#manage) shares them. You share a skill from [Catalog Explorer](/aws/en/catalog-explorer/) by granting `READ VOLUME`.

**Permissions required:** you must be the skill's owner or have `MANAGE` on it.

1. In your Databricks workspace, click  **Catalog**.
2. Navigate to the schema that holds the skill, then select the skill.
3. Go to the **Permissions** tab.
4. Click **Grant**.
5. Enter the email address for a user or the name of a group.
6. Select `READ VOLUME`.
7. Click **OK**.

Recipients also need `USE CATALOG` on `acme` and `USE SCHEMA` on `sql_skills` to reach the skill. Grant those on the catalog and schema the same way. To revoke access later, select the grant on the **Permissions** tab and click **Revoke**.

Sharing a skill grants access to the live skill. The recipient's agent reads it under the skill's grants and audit, so there is nothing to keep in sync. For the full privilege model, see [Govern skills](/aws/en/ai-gateway/govern-skills).

After you share a skill, teammates find and use it from their own agents. See [Discover and use Unity Gateway Skills](/aws/en/agents/uc-skills/use-uc-skills).

## Publish skills from your GitHub repository

If you already use GitHub to manage your skills, use the [Unity Gateway skill publishing action](https://github.com/databricks/unity-gateway/tree/main/actions/publish-skills) to create and update their Unity Catalog counterparts. You need permission to add a workflow to the repository that holds your skills. The workflow publishes from a GitHub runner after changes merge to your publishing branch. You do not need a Databricks notebook, cluster, or scheduled job.

For an upstream repository where you cannot configure workflows, see [Advanced: Sync an upstream Git repository](#sync-a-git-skill-repository-to-a-uc-schema).

### Set up publishing access

A Databricks admin and a GitHub repository admin complete this setup:

1. Create or select a publishing [service principal](/aws/en/admin/users-groups/service-principals), [assign it to the target workspace](/aws/en/admin/users-groups/manage-service-principals#assign-sp-workspace), and grant it the catalog and schema privileges in [Requirements](#requirements) on every destination schema. For existing skills it updates, also grant [`READ VOLUME`](/aws/en/data-governance/unity-catalog/access-control/privileges-reference#read-volume) and [`WRITE VOLUME`](/aws/en/data-governance/unity-catalog/access-control/privileges-reference#write-volume). New skills are owned by the publishing principal, so grant `MANAGE` on every destination schema to the users or group who share the skills. They also need `USE CATALOG` and `USE SCHEMA` on the parent catalog and schema. The schema grant applies to its child skills. See [Privilege inheritance](/aws/en/data-governance/unity-catalog/access-control/permissions-concepts#inheritance).
2. Create a [GitHub environment](https://docs.github.com/en/actions/how-tos/write-workflows/choose-what-workflows-do/deploy-to-environment) named `production` in your skills repository. Restrict its deployment branches to `main`, or the branch you intend to publish from.
3. Configure [GitHub workload identity federation](/aws/en/dev-tools/auth/provider-github) on the publishing service principal. Match the exact OpenID Connect (OIDC) subject for your skills repository and the `production` environment. GitHub issues a short-lived identity token that the Databricks SDK exchanges for a Databricks access token, so no Databricks client secret is stored in GitHub. Newer repositories can include numeric organization and repository IDs in their subject. Follow the federation guide to configure the subject and audience for your repository.
4. In **Settings > Environments > production > Environment variables**, add `DATABRICKS_HOST` with your workspace base URL and `DATABRICKS_CLIENT_ID` with the service principal's application ID. Neither value is secret.
5. Choose a Linux runner that can reach your workspace. The example uses a GitHub-hosted runner. A workspace with private networking or [IP access lists](/aws/en/security/network/front-end/ip-access-list) might require a runner on your network.

For detailed administrator instructions and an OAuth machine-to-machine alternative, see the action's [authentication guide](https://github.com/databricks/unity-gateway/blob/main/actions/publish-skills/docs/authentication.md).

The examples reference the action at `main`, so they pick up its latest updates. For reproducible workflows, replace `main` in the action reference with a reviewed commit SHA from the Unity Gateway repository. You do not need to install the Unity Gateway CLI.

### Add the workflow

1. Add your skills to the repository. Each immediate child folder of `skills` that contains `SKILL.md` becomes a skill. Supporting files in each folder are included:

   Text

   ```
   skills/

   ├── sql-guide/

   │   ├── SKILL.md

   │   └── references/conventions.md

   └── code-review/

   └── SKILL.md
   ```

   The folder basename determines the Unity Catalog skill identifier when using `skills-directory`: `skills/sql-guide` becomes `acme.team_skills.sql-guide`. The `name` in `SKILL.md` remains required skill metadata, but the action does not use it to choose the Unity Catalog identifier. For clarity, use `name: sql-guide` in this example. An explicit mapping uses its `target` value instead of the folder basename.

   For skill contents and frontmatter, see [Develop a skill locally](#develop-a-skill-locally).
2. Create `.github/workflows/publish-skills.yml` with the following content. Replace `acme.team_skills` with your existing catalog and schema. If your publishing branch or source folder differs, update the branch and path filters as well.

   YAML

   ```
   name: Publish skills to Databricks

   on:

   push:

   branches: [main]

   paths: ['skills/**', '.github/workflows/publish-skills.yml']

   workflow_dispatch:

   inputs:

   dry_run:

   description: Validate folders without publishing

   type: boolean

   default: true

   permissions:

   contents: read

   id-token: write

   concurrency:

   group: publish-uc-skills

   cancel-in-progress: false

   jobs:

   publish:

   runs-on: ubuntu-latest

   environment: production

   env:

   DATABRICKS_AUTH_TYPE: github-oidc

   DATABRICKS_HOST: ${{ vars.DATABRICKS_HOST }}

   DATABRICKS_CLIENT_ID: ${{ vars.DATABRICKS_CLIENT_ID }}

   steps:

   - uses: actions/checkout@34e114876b0b11c390a56381ad16ebd13914f8d5 # v4.3.1

   with:

   persist-credentials: false

   - uses: databricks/unity-gateway/actions/publish-skills@main

   with:

   skills-directory: skills

   target-schema: acme.team_skills

   dry-run: ${{ github.event_name == 'workflow_dispatch' && inputs.dry_run || false }}
   ```

   This maps `skills/sql-guide` to `acme.team_skills.sql-guide` and `skills/code-review` to `acme.team_skills.code-review`.
3. Merge the workflow and skills to `main`. This triggers the first publication. To validate source files in pull requests before publishing, add the action's [validation workflow](https://github.com/databricks/unity-gateway/blob/main/actions/publish-skills/examples/validate-skills.yml). Dry runs validate local skill folders without contacting Databricks. They do not test authentication, network access, or permissions. Because the `production` environment allows only `main`, run manual dry runs from `main` and use the validation workflow to check other branches.
4. In GitHub, open **Actions > Publish skills to Databricks** and check the run logs. In Databricks, open Catalog Explorer and confirm that the skills appear in your target schema. After the workflow is on `main`, you can also select **Run workflow** and leave **Validate folders without publishing** selected for a dry run, or clear it to publish.
