This page explains how to serve many end users through a single service principal while each user sees only their own data. Your application adds a custom identity claim to the OAuth token it requests for the service principal. A dynamic view or an attribute-based access control (ABAC) policy then compares the claim to a column and returns only the matching rows. You don't need to create a Databricks user for each end user.

The claim is signed into the OAuth token when the token is created, and it passes through to the SQL engine when the token authenticates. In SQL, you read the claim with the [`current_oauth_custom_identity_claim`](/aws/en/sql/language-manual/functions/current_oauth_custom_identity_claim) function.

warning

Databricks doesn't encrypt or interpret the claim. Anyone who holds the token can decode it and read the claim, so never put secrets or sensitive data in it.

## How it works

For example, a company sells to many business customers and stores every customer's orders in one table. Customers query their orders through the company's application:

1. The application authenticates the customer and decides on its own server which claim the customer gets, for example `acme`.
2. The application creates an OAuth token for its service principal with `custom_claim=acme`.
3. The application queries Databricks with that token through JDBC, the SQL Statement Execution API, or the Genie Agents API.
4. A dynamic view or ABAC policy compares a column to `current_oauth_custom_identity_claim()` and returns only Acme's orders.

## Requirements

* A service principal assigned to the workspace, with either an OAuth secret for the client credentials grant or a federation policy for the token exchange grant. See [Authorize service principal access to Databricks with OAuth](/aws/en/dev-tools/auth/oauth-m2m) and [Configure a federation policy](/aws/en/dev-tools/auth/oauth-federation-policy).
* A SQL warehouse. See [Create a SQL warehouse](/aws/en/compute/sql-warehouse/create).
* Compute running Databricks Runtime 19.7 or above. See [`current_oauth_custom_identity_claim` function](/aws/en/sql/language-manual/functions/current_oauth_custom_identity_claim).

## Supported surfaces

The claim reaches the SQL engine only when the request authenticates with the OAuth token that carries it. The following surfaces support custom identity claims:

* The [Databricks JDBC Driver](/aws/en/integrations/jdbc-oss/) connected to a SQL warehouse
* The [SQL Statement Execution API](/aws/en/dev-tools/sql-execution-tutorial) on a SQL warehouse
* The [Use the Genie Agents API](/aws/en/genie-agents/conversation-api)

Surfaces that don't use a custom-claim OAuth token, such as the SQL editor in the workspace UI, don't support custom identity claims.

## Step 1: Create a dynamic view that filters on the claim

In this example, the table `main.sales.orders` stores every customer's orders. Each row records an order and the name of the customer who placed it:

| order\_id | customer\_name | product | quantity | price | order\_date |
| --- | --- | --- | --- | --- | --- |
| 1 | acme | bottling line | 2 | 120000 | 2026-01-02 |
| 2 | globex | display shelf | 40 | 350 | 2026-01-23 |
| 3 | acme | delivery truck | 5 | 85000 | 2026-02-03 |

←✕

| order\_id | customer\_name | product | quantity | price | order\_date |
| --- | --- | --- | --- | --- | --- |
| 1 | acme | bottling line | 2 | 120000 | 2026-01-02 |
| 2 | globex | display shelf | 40 | 350 | 2026-01-23 |
| 3 | acme | delivery truck | 5 | 85000 | 2026-02-03 |

As the data owner, create a dynamic view that returns only the rows where `customer_name` matches the claim in the caller's token:

SQL

```
CREATE OR REPLACE VIEW main.sales.customer_orders AS

SELECT order_id, customer_name, product, quantity, price, order_date

FROM main.sales.orders

WHERE customer_name = current_oauth_custom_identity_claim();
```

When the application queries `customer_orders` with a token that carries the `acme` claim, the view returns orders 1 and 3. With the `globex` claim, it returns order 2.

See [Create a dynamic view](/aws/en/views/dynamic). To filter the table with an ABAC policy instead of a view, see [Filter with an ABAC policy instead of a dynamic view](#abac).

### Write filters that match no rows when the claim is NULL

warning

`current_oauth_custom_identity_claim()` returns `NULL` for any token without a custom claim, including tokens your application creates by mistake without one. Write every filter so that a `NULL` claim matches no rows.

The filter in the previous example is safe. Comparing a column to `NULL` with `=` never returns true, so a token without a claim gets no rows. Other filters do the opposite and return rows when the claim is missing. For a token without a claim, each of the following filters returns other customers' data:

SQL

```
-- Don't use any of these filters.

WHERE current_oauth_custom_identity_claim() IS NULL OR customer_name = current_oauth_custom_identity_claim()

WHERE customer_name = coalesce(current_oauth_custom_identity_claim(), customer_name)

WHERE (customer_name = current_oauth_custom_identity_claim()) IS NOT FALSE

WHERE (customer_name <> current_oauth_custom_identity_claim()) IS NOT TRUE
```

The same applies to a row filter function such as `RETURN claim IS NULL OR customer_name = claim`.

Also avoid the null-safe equality operator `customer_name <=> current_oauth_custom_identity_claim()`. With a `NULL` claim, it matches every row whose `customer_name` is `NULL`.

Use the claim only as a value to compare. Don't use it as a pattern in `RLIKE`, as an object name in `IDENTIFIER`, or as part of the SQL text that `EXECUTE IMMEDIATE` runs. Treat the claim like any other untrusted input.

### Map end-user identities to data with a mapping table

The previous example puts the customer name directly in the claim. To carry the identity of each end user instead, such as an email address, put the user ID in the claim and join a mapping table that assigns each user to the data they can see. To change a user's access, you update a row in the mapping table. You don't need to change how the application creates tokens.

SQL

```
CREATE OR REPLACE TABLE main.sales.customer_users (

user_id STRING,

customer_name STRING

);

INSERT INTO main.sales.customer_users VALUES

('alice@acme.example.com',   'acme'),

('bob@acme.example.com',     'acme'),

('carol@globex.example.com', 'globex');

CREATE OR REPLACE VIEW main.sales.customer_orders AS

SELECT o.order_id, o.customer_name, o.product, o.quantity, o.price, o.order_date

FROM main.sales.orders AS o

JOIN main.sales.customer_users AS u

ON o.customer_name = u.customer_name

WHERE u.user_id = current_oauth_custom_identity_claim();
```

The application then creates each user's token with the user's ID as the claim, for example `custom_claim=alice@acme.example.com`. A user who isn't in the mapping table, or a token without a claim, matches no rows.

The view reads the mapping table with the view owner's privileges, so the service principal doesn't need access to it.

## Step 2: Grant the service principal access

Grant the service principal only the privileges it needs to query the view.

1. Grant the service principal the **Can use** permission on the SQL warehouse. See [Manage a SQL warehouse](/aws/en/compute/sql-warehouse/create#manage).
2. Grant the service principal `USE CATALOG`, `USE SCHEMA`, and `SELECT` on the view. Run the following as the data owner, or grant the same privileges in [Catalog Explorer](/aws/en/catalog-explorer/):

   SQL

   ```
   GRANT USE CATALOG ON CATALOG main TO `<service-principal-application-id>`;

   GRANT USE SCHEMA ON SCHEMA main.sales TO `<service-principal-application-id>`;

   GRANT SELECT ON VIEW main.sales.customer_orders TO `<service-principal-application-id>`;
   ```

important

Don't grant the service principal any privileges on the underlying table or the mapping table, and don't grant broad privileges such as `ALL PRIVILEGES` on the schema or catalog. A service principal that can read the underlying table can query it directly and bypass the dynamic view. A service principal that can read the mapping table can see every user and the data each one has access to.

## Step 3: Create an OAuth token with a custom claim

Your application creates a token for each end user by adding the `custom_claim` parameter to a token request. Use the client credentials grant or the token exchange grant. Always decide the claim on your server from the user's authenticated session, never from request input.

### Client credentials

Send the service principal's client ID and secret, and add `custom_claim`:

Bash

```
curl --request POST \

--url https://<workspace-url>/oidc/v1/token \

--user '<client-id>:<client-secret>' \

--data 'grant_type=client_credentials' \

--data 'scope=all-apis' \

--data-urlencode 'custom_claim=acme'
```

To create an account-level token with a claim, send the same request to `https://<account-console-url>/oidc/accounts/<account-id>/v1/token`.

See [Manually generate OAuth M2M access tokens](/aws/en/dev-tools/auth/oauth-m2m#oauth-m2m-manual).

### Token exchange

If you use [workload identity federation](/aws/en/dev-tools/auth/oauth-federation), exchange the workload's identity token for a Databricks OAuth token, and add `custom_claim`:

Bash

```
curl --request POST \

--url https://<workspace-url>/oidc/v1/token \

--data 'client_id=<service-principal-application-id>' \

--data 'subject_token=<identity-provider-jwt>' \

--data 'subject_token_type=urn:ietf:params:oauth:token-type:jwt' \

--data 'grant_type=urn:ietf:params:oauth:grant-type:token-exchange' \

--data 'scope=all-apis' \

--data-urlencode 'custom_claim=acme'
```

If the token you exchange already carries a custom claim, the new token keeps that claim, and you can't set a different one.

### Requirements for the claim value

A request whose claim doesn't meet these requirements fails with `400 invalid_request`:

* The claim can contain printable ASCII characters: letters, digits, spaces, and punctuation. Tab (`\t`), newline (`\n`), and carriage return (`\r`) are also allowed, so the claim can hold multi-line text such as formatted JSON.
* Other control characters and non-ASCII characters, such as accented letters and emoji, aren't allowed.
* The claim can't be empty or contain only whitespace, and it can be at most 1,000 characters.

To create a token without a claim, omit the `custom_claim` parameter.

### Check the claim in a token

The token is a JSON Web Token (JWT). If you decode it, the claim appears in the payload:

JSON

```
"custom": { "claim": "acme" }
```

To see which claim a token carries, call token introspection with the token. For a workspace-level token:

Bash

```
curl --request GET \

--url https://<workspace-url>/api/2.0/tokens/introspect \

--header "authorization: Bearer <access-token>"
```

For an account-level token, call `https://<account-console-url>/api/2.0/accounts/<account-id>/tokens/introspect`.

The response includes `oauth_custom_claim` only when the token carries a custom claim. The following example shows the relevant fields of the response:

JSON

```
{

"principal_context": {

"authorizing_principal": {

"unique_principal_name": "<service-principal-application-id>",

"principal_type": { "service_principal_type": "SERVICE_PRINCIPAL_TYPE_USER_MANAGED" },

"display_name": "<service-principal-name>"

},

"authentication_scope": {

"account_id": "<account-id>",

"workspace_id": <workspace-id>

},

"oauth_custom_claim": "acme"

}

}
```

## Step 4: Query the view with the token

The following Java example uses the [Databricks JDBC Driver](/aws/en/integrations/jdbc-oss/) to query the view on a SQL warehouse with the token from the previous step.

1. Copy the **JDBC URL** from the **Connection details** tab of the SQL warehouse.
2. In the URL, replace `AuthMech=3` with `AuthMech=11;Auth_Flow=0;` to authenticate with an OAuth token.
3. Append the token to the URL, connect, and query the view:

   Java

   ```
   String oauthToken = "<oauth-token-with-custom-claim>";

   String jdbcUrl = "jdbc:databricks://<workspace-url>:443/default;transportMode=http;ssl=1;"

   + "httpPath=/sql/1.0/warehouses/<warehouse-id>;AuthMech=11;Auth_Flow=0;"

   + "Auth_AccessToken=" + oauthToken + ";";

   try (Connection connection = DriverManager.getConnection(jdbcUrl);

   ResultSet rs = connection.prepareStatement("SELECT * FROM main.sales.customer_orders").executeQuery()) {

   while (rs.next()) {

   System.out.println(rs.getLong("order_id") + "\t" + rs.getString("customer_name") + "\t"

   + rs.getString("product") + "\t" + rs.getString("order_date"));

   }

   }
   ```

With the `acme` token, the query returns only Acme's orders:

```
1	acme	bottling line	2026-01-02

3	acme	delivery truck	2026-02-03
```

With the `globex` token, the same query returns only Globex's order:

```
2	globex	display shelf	2026-01-23
```

The same tokens work with the [SQL Statement Execution API](/aws/en/dev-tools/sql-execution-tutorial) and the [Use the Genie Agents API](/aws/en/genie-agents/conversation-api). For a Genie example, see [Example: customer order assistant with a Genie Agent](#genie-example).
