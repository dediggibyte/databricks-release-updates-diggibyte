This feature is in [Beta](/aws/en/release-notes/release-types). Reach out to your Databricks account team to enable this feature in your account.

Lakehouse//RT is in active development. Performance characteristics and the supported feature set will change before general availability.

Lakehouse Real-Time (Lakehouse//RT) is a serverless compute built for low-latency, high-concurrency use cases, such as serving analytical data to custom applications, running operational analytics, or powering BI dashboards that require sub-second responses for hundreds to thousands of concurrent users.

Lakehouse//RT offers sub-second latency on SQL read queries against your Unity Catalog tables that use Delta Lake or Apache Iceberg formats in cloud storage. You create and manage Lakehouse//RT much like you do other SQL warehouses. A workspace admin or privileged user creates one or more per workspace and assigns permissions to users.

## Requirements

To use Lakehouse//RT, you must:

* Be in a [supported region](/aws/en/resources/feature-region-support#serverless-aws).
* Have the Lakehouse//RT Beta enabled in your workspace.

## Enable Lakehouse//RT in your workspace

Workspace admins can enable the Lakehouse//RT Beta in your workspace:

1. In your workspace menu (top-right corner), go to **Previews**.
2. Search for **Lakehouse RT**.
3. Enable the preview.

After you enable the preview, the **Real-Time** warehouse type becomes available in the SQL warehouse creation flow for your workspace.

## Create a Lakehouse//RT warehouse

To create a Lakehouse//RT warehouse:

1. Go to **Compute** > **SQL Warehouses** > **Create SQL Warehouse**.
2. Select **Real-Time**.
3. Select a **Query size**: **Small**, **Medium**, **Large**, or **X-Large**, depending on the performance your queries require.
4. Configure the **Autoscaling** to determine the maximum DBUs you can be billed per hour.
5. Set **Auto stop** to control when an idle warehouse stops.
6. Enter a name for the warehouse.
7. Click **Create**.

To assign permissions, grant **Can use**, **Can monitor**, or **Can manage** to users and groups, the same as a SQL warehouse.

note

You cannot currently upgrade an existing SQL warehouse to Lakehouse//RT or downgrade an existing Lakehouse//RT warehouse to another warehouse type.

## Size and scale a Lakehouse//RT warehouse

Lakehouse//RT has settings that control performance and cost:

* **Query size** controls the compute available to a single query.
* **Autoscaling** controls how much the warehouse scales out to serve concurrent queries.
* **Auto stop** controls how long an idle warehouse keeps running before it stops.

Query size and autoscaling work differently from the sizing and scaling settings on a serverless SQL warehouse.

### Query size

The query size sets the maximum compute a single query can use, which determines how fast an individual query can run. It also sets the minimum compute the warehouse runs on, and the minimum you are billed for, while the warehouse is up.

You set the query size when you create the warehouse. Choose **Small**, **Medium**, **Large**, or **X-Large**. A larger size gives each query more compute for faster results, at a higher minimum cost.

This setting is similar in concept to the size of a serverless SQL warehouse, which also sets the compute available to a single query.

### Autoscaling

Autoscaling lets a warehouse add compute to serve more concurrent queries, then release it when demand drops. You set the maximum compute the warehouse can scale up to, measured in DBUs.

Autoscaling on Lakehouse//RT differs from cluster scaling on a serverless SQL warehouse in a few ways:

* It is measured in DBUs, not clusters.
* The maximum is independent of query size. You can pair a small query size with a high maximum to get high concurrency without giving each query more compute.
* Lakehouse//RT autoscaling adds and removes just the compute needed, instead of in increments of clusters.

To see how much a warehouse is scaling, use its [monitoring page](/aws/en/compute/sql-warehouse/monitor/).

### Auto stop

Auto stop terminates the warehouse after it's idle for a set number of minutes, so an idle warehouse doesn't keep accruing charges. You set the idle timeout when you create the warehouse.

Auto stop on Lakehouse//RT works the same as on a serverless SQL warehouse. For the default and minimum values, see [Configure SQL warehouse settings](/aws/en/compute/sql-warehouse/create#settings).

## Monitor Lakehouse//RT activity

You can monitor Lakehouse//RT queries the same as any query run on a SQL warehouse:

* **Query history:** Lakehouse//RT queries appear in the [query history UI](/aws/en/sql/user/queries/query-history) and the [query history system table](/aws/en/admin/system-tables/query-history).
* **Query profiles:** Open a Lakehouse//RT query in the query history UI to view its [query profile](/aws/en/sql/user/queries/query-profile).
* **Monitoring page:** Monitor query throughput, queued queries, and query history on the [monitoring page](/aws/en/compute/sql-warehouse/monitor/) for each Lakehouse//RT warehouse.
* **Billing:** Lakehouse//RT usage appears in the billing system tables with a `sku_name` of `Lakehouse_Serverless`.

## Best practices

To get the best results from Lakehouse//RT, prepare your workloads before you move them over:

* **Validate on serverless SQL first.** Run your queries on a serverless SQL warehouse and confirm that they run in a few seconds.
* **Use Unity Catalog managed tables.** Managed tables with [predictive optimization](/aws/en/optimizations/predictive-optimization) and [liquid clustering](/aws/en/tables/clustering) ensure that your data is well clustered for your workload patterns.
* **Verify queries are selective.** For sub-second latency, verify that your queries scan lesser amounts of data. Filter early with `WHERE` clauses, select only the columns you require, and lean on aggregations. Joining across tables is supported, but if you find your query getting complex or slow, consider using materialized views that pre-aggregate your data for faster latencies.
* **Check SQL coverage.** Lakehouse//RT supports ANSI-compliant read queries only. Confirm that your workloads are [ANSI compliant](/aws/en/sql/language-manual/sql-ref-ansi-compliance#sql-functions) and avoid the unsupported statements, functions, and data types listed under [Limitations](#limitations).

To build AI/BI dashboards on a Lakehouse//RT warehouse, including guardrails and dashboard-specific limitations, see [Use Lakehouse Real-Time with AI/BI dashboards](/aws/en/compute/sql-warehouse/real-time-dashboards).

### Table types

Lakehouse//RT queries Unity Catalog data only. For best performance, use Unity Catalog managed tables, which provide the engine with the data layout it needs for low latency.

Lakehouse//RT supports the following table types:

* Managed tables (Delta Lake and Apache Iceberg tables)
* Materialized views and streaming tables
* Metric views

### Connectivity

Lakehouse//RT only accepts connections that use the [Statement Execution API](https://docs.databricks.com/api/statement-execution/v1/statement-execution). It does not support the legacy Thrift protocol, so a driver that connects without explicitly using the Statement Execution API receives a `501` error.

You can connect to a Lakehouse//RT warehouse in the following ways:

* **Statement Execution API:** Call the API directly from external applications. See [Statement Execution API: Run SQL on warehouses](/aws/en/dev-tools/sql-execution-tutorial).
* **Databricks drivers:** The following drivers can connect using the Statement Execution API. Point the driver's HTTP path at your Lakehouse//RT warehouse, then follow the configuration listed for the driver:
  + **[Databricks SQL Connector for Python](/aws/en/dev-tools/python-sql-connector#statement-execution-api):** Set `use_kernel=True`.
  + **[Databricks SQL Driver for Node.js](/aws/en/dev-tools/nodejs-sql-driver#statement-execution-api):** Set `useKernel: true`.
  + **[Databricks SQL Driver for Go](/aws/en/dev-tools/go-sql-driver#statement-execution-api):** Build with the `databricks_kernel` tag and set `WithUseKernel(true)`.
  + **[JDBC](/aws/en/integrations/jdbc-oss/properties):** Set `UseThriftClient=0` in the connection URL.
  + **[ADBC driver for Power BI](/aws/en/partners/bi/power-bi/adbc#real-time):** Set `Implementation=2.0` and `Protocol=REST(SEA)` under **Advanced options**.
  + **[Databricks OSS ODBC Driver (Beta)](/aws/en/integrations/odbc-oss/):** No additional configuration is required. The driver supports SQL warehouses, including Lakehouse//RT, but not all-purpose compute.
* **[Databricks Excel Add-in](/aws/en/integrations/excel/):** Select your Lakehouse//RT warehouse in the add-in's compute selector. Only imports are supported.

## Fine-grained access control

Lakehouse//RT supports read queries on tables protected by row filters and column masks. The filters and masks can be assigned directly to a table or applied through attribute-based access control (ABAC) policies. See [Row filters and column masks](/aws/en/data-governance/unity-catalog/filters-and-masks/) and [Attribute-based access control in Unity Catalog](/aws/en/data-governance/unity-catalog/abac/).

Use compute that supports policy management, such as a serverless SQL warehouse, to create or change row filters, column masks, and ABAC policies. Lakehouse//RT applies existing policies when reading tables. It does not support policy management statements or writes to tables with policies. For query restrictions, see [Fine-grained access control limitations](#fine-grained-access-control-limitations).

### Column mask result types

Lakehouse//RT casts the result of a column mask back to the column's declared data type using ANSI semantics. This applies to both table-level masks and ABAC masks. If the result cannot be cast to the column's type, the query fails.

For example:

* A mask that returns the string `'REDACTED'` for a `BOOLEAN` column causes the query to fail because the string cannot be cast to `BOOLEAN`.
* A mask that returns `FALSE` for an `INT` column produces the integer `0`.

On Databricks Runtime, a table-level column mask exposes the mask's return type to the query. Moving the same query to Lakehouse//RT can change its result type or cause a cast error. ABAC masks cast results back to the column type on both Databricks Runtime and Lakehouse//RT. Databricks recommends masking functions that return the same type as the column.

### Query plans and profiles for protected tables

For queries that use row filters or column masks, Lakehouse//RT limits the details shown in `EXPLAIN` output and [query profiles](/aws/en/sql/user/queries/query-profile) to protect information about the underlying data and policy logic:

* `EXPLAIN` output hides query steps that read protected data or apply policies. It also omits plan statistics.
* Query profiles hide these query steps and omit statistics for protected tables.

## Limitations

When a query uses an unsupported feature, Lakehouse//RT returns an error naming the feature. To successfully run the query, use a serverless SQL warehouse instead.

### Tools and features

Lakehouse//RT does not yet support the following features:

* Genie
* Genie Agents
* Jobs tasks

### Table types

The following table types are not yet supported:

* System tables
* Delta Sharing tables
* Tables in Unity Catalog default storage
* External tables in Unity Catalog

Lakehouse//RT does not support the following table types:

* Hive metastore tables (managed or external)
* Foreign tables and query federation (Lakehouse Federation)
* Temporary tables
* Tables that use other data formats (CSV, JSON, Avro, Parquet, ORC, and text)

### Fine-grained access control limitations

Queries involving row filters or column masks have the following limitations:

* Change data feed reads using `table_changes` are not supported on protected tables.
* ABAC policies attached to views are not supported.
* Queries on tables with ABAC policies that use `system.builtin` functions fail with `ABAC_BUILTIN_FUNCTION_NOT_SUPPORTED`.
* Multiple `DISTINCT` argument sets in an aggregate inside a policy function fail with `UNSUPPORTED_FEATURE`. Aggregates that share the same `DISTINCT` arguments and aggregates in the outer query remain supported.
* Some correlated subqueries involving tables with row filters or column masks are not supported and return an `UNSUPPORTED_FEATURE` error.

### Drivers and connectors

Lakehouse//RT does not support the Simba Spark ODBC Driver or the Databricks ODBC Driver. Use the [Databricks OSS ODBC Driver](/aws/en/integrations/odbc-oss/) instead.

### SQL language

Lakehouse//RT runs SQL read queries in [ANSI mode](/aws/en/sql/language-manual/sql-ref-ansi-compliance) only. It evaluates all implicit type coercions and casts according to strict ANSI SQL rules, and this behavior cannot be turned off. Under ANSI semantics, queries that relied on non-ANSI behavior might:

* Raise a runtime error instead of silently producing `NULL`. For example, casting a non-numeric string to a number.
* Raise an analysis-time error when there is no safe common type. For example, `COALESCE`, `CASE`, `IN`, or set operations across incompatible types.
* Return a different result type than legacy mode, because ANSI string promotion and numeric widening choose safe, lossless types.

To get predictable results, use explicit `CAST` expressions when ANSI mode implicit conversions don't produce the behavior you expect.
