Preview

This feature is in [Public Preview](/aws/en/release-notes/release-types). Workspace admins can control access to **DataFrame caching on serverless compute** from the **Previews** page. See [Manage Databricks previews](/aws/en/admin/workspace-settings/manage-previews).

On serverless compute, you can cache a DataFrame with `df.cache()` or `df.persist()` to reuse an expensive result in your session. Databricks computes the DataFrame when you call `cache()` and materializes the result as a snapshot. The DataFrame and the DataFrames you build from it then read the snapshot for the rest of your session instead of recomputing it.

## Requirements

* The **DataFrame caching on serverless compute** preview is enabled for your workspace (enabled by default). Workspace admins can disable it from the **Previews** page. The preview isn't available in workspaces with the [compliance security profile](/aws/en/security/privacy/security-profile) enabled. See  [Manage workspace-level previews](/aws/en/admin/workspace-settings/manage-previews#workspace).
* Notebooks and jobs on serverless compute must use [environment version](/aws/en/compute/serverless/dependencies) 5 or above.
* Databricks Connect for Python must be 18.1.8 or above, and Databricks Connect for Scala must be 18.1.5 or above.

Older clients get the `CACHE_REQUIRES_NEWER_CLIENT_ON_SERVERLESS_GC` error.

## When to use DataFrame caching on serverless compute

Cache a DataFrame on serverless compute when you need to:

* Reuse the result of an expensive join, aggregation, or filter several times in the same session.
* Compute a streaming micro-batch one time in a `foreachBatch` function, then write it to several sinks.
* Train or tune several machine learning models on the same prepared feature data.
* Keep a stable snapshot while you run several steps of an analysis, even if the source tables change.

See [Best practices](#best-practices).

## Cache DataFrame APIs on serverless compute

The following example caches one day of orders joined with customer data, computes the day's total revenue, appends the revenue by region to a report table, and then releases the cache. Both results read the cached snapshot instead of running the join again.

* Python
* Scala

Python

```
from pyspark.sql import functions as F

# The DataFrame to cache: one day of orders joined with customer data.

oct_15_orders = (

spark.table("main.sales.orders")

.filter(F.col("order_date") == "2026-10-15")

.join(spark.table("main.sales.customers"), "customer_id")

)

oct_15_orders.cache()

# Both results are built from oct_15_orders, so they read the cached snapshot.

total_revenue = oct_15_orders.agg(F.sum("amount")).first()[0]

print(f"Total revenue on 2026-10-15: {total_revenue}")

revenue_by_region = oct_15_orders.groupBy("order_date", "region").agg(F.sum("amount").alias("revenue"))

revenue_by_region.write.mode("append").saveAsTable("main.reports.revenue_by_region")

# Release the cache and the DataFrame when you no longer need it.

# oct_15_orders and DataFrames built from it can no longer be used.

oct_15_orders.unpersist()
```

Scala

```

// oct15Orders and DataFrames built from it can no longer be used.

```

In the following API descriptions, `df` stands for any DataFrame in your session, such as `oct_15_orders` in the preceding example.

### `df.cache()`

Computes `df` right away and caches the result as a *snapshot* for the rest of your session.

* **Returns**: The same cached DataFrame, `df`, now based on the snapshot instead of the computation on its source tables. See the following behavior.
* **Behavior**:
  + Runs the DataFrame's query right away and materializes the result as a snapshot before the call returns.
  + After the call, `df` and the returned DataFrame (`df` itself) are based on the snapshot. They are no longer connected to the computation on the source tables, so they read the snapshot instead of recomputing the query.
  + DataFrames derived from `df`, directly or through other derived DataFrames, read the snapshot automatically instead of running the original query again. See [Read the snapshot](#read-snapshot).
  + The snapshot is local to your session. Only the session that cached `df` can read it. See [Isolation and privileges](#isolation).
  + The snapshot lasts until the session ends, for at most seven days. Databricks then automatically reclaims its storage in the background. Calling [`df.unpersist()`](#unpersist) allows it to reclaim the storage earlier. See [Lifecycle and time limits](#lifecycle) and [Storage and cleanup](#storage).
  + If computing `df` fails, `df.cache()` raises the error and `df` isn't cached.
  + Calling `df.cache()` on a DataFrame that is already cached does nothing. `df` isn't computed again.

The snapshot is fixed after you call `df.cache()`. Data written afterward to the tables that `df` reads from, and schema changes to those tables such as added or renamed columns, don't affect it. To recompute from the latest data, build the DataFrame again from the source tables, and cache the new DataFrame if you need to.

### Read the snapshot

On serverless compute, cache matching is based on DataFrame derivation. After `df.cache()`, only the following DataFrames read the snapshot automatically instead of recomputing the query on the source tables:

* The DataFrame you cached, `df`.
* DataFrames derived from `df`, for example with `select()`, `filter()`, `groupBy()`, or `join()`.
* DataFrames further chained from those derived DataFrames.

A new DataFrame that repeats the same query reads the source tables, even though its logic is identical, because it isn't derived from `df`.

This makes cache matching explicit and under your control: a DataFrame reads cached data only when you derive it from a cached DataFrame. Every other DataFrame reads the source tables.

* Python
* Scala

Python

```
oct_15_orders = (

spark.table("main.sales.orders")

.filter(F.col("order_date") == "2026-10-15")

.join(spark.table("main.sales.customers"), "customer_id")

)

# The join runs one time, when you call cache().

oct_15_orders.cache()

# Derived from oct_15_orders: read the snapshot, so the join doesn't run again.

large_orders = oct_15_orders.filter(F.col("amount") > 1000)

revenue_by_region = oct_15_orders.groupBy("order_date", "region").agg(F.sum("amount").alias("revenue"))

# Derived from large_orders, which is derived from oct_15_orders: also reads the snapshot.

large_orders_by_region = large_orders.groupBy("region").count()

# Not derived from oct_15_orders: reads the source tables and runs the join again.

same_query = (

spark.table("main.sales.orders")

.filter(F.col("order_date") == "2026-10-15")

.join(spark.table("main.sales.customers"), "customer_id")

)
```


Because `df` reads the snapshot instead of the DataFrames it was built from, you can't reference the columns of `df` through those DataFrames. See [Limitations](#limitations).

### `df.persist(storageLevel)`

An alias of `df.cache()` that accepts a storage level.

* **Parameters**:
  + `storageLevel` (optional): A `StorageLevel`, such as `StorageLevel.DISK_ONLY`. serverless compute accepts any storage level and ignores it. The snapshot is stored the same way for every storage level, and `df.storageLevel` returns `StorageLevel.DISK_ONLY`.

The return value and behavior are the same as `df.cache()`.

### `df.unpersist(blocking)`

Releases the cached snapshot of `df` and destroys the DataFrame.

* **Parameters**:
  + `blocking` (optional): Ignored. `df.unpersist()` returns right away for either value.
* **Returns**: The same DataFrame, `df`, now destroyed.
* **Behavior**:
  + Marks the snapshot as ready to be reclaimed. Databricks then deletes the cached data and reclaims the storage in the background.
  + Destroys `df`: `df` and any DataFrames previously derived from it are no longer usable, and any subsequent query on them raises `CACHE_DATAFRAME_ACCESS_AFTER_UNCACHE`. If you cache a DataFrame derived from `df` before you call `df.unpersist()`, that DataFrame stays usable, because it has its own snapshot.
  + To continue working with the same data source, build a new DataFrame from the original data source, instead of reusing the uncached DataFrame.
  + Calling `df.unpersist()` on a DataFrame that was never cached, or that has already been uncached, is a no-op.

Call `df.unpersist()` when you no longer need the cached data, for example when no later step in your notebook or job reads it. This allows Databricks to reclaim the storage earlier. Don't use `df.unpersist()` to refresh data. To work with the latest data, build a new DataFrame from the source tables.

* Python
* Scala

Python

```
oct_15_orders = spark.table("main.sales.orders").filter(F.col("order_date") == "2026-10-15")

oct_15_orders.cache()

large_orders = oct_15_orders.filter(F.col("amount") > 1000)

orders_per_customer = oct_15_orders.groupBy("customer_id").count()

orders_per_customer.cache()  # Has its own snapshot.

# Acknowledge that the cached data is no longer needed.

# This releases the storage and destroys oct_15_orders.

oct_15_orders.unpersist()

oct_15_orders.count()  # Raises CACHE_DATAFRAME_ACCESS_AFTER_UNCACHE.

large_orders.count()  # Raises CACHE_DATAFRAME_ACCESS_AFTER_UNCACHE.

orders_per_customer.count()  # Reads its own snapshot.

# If you need the data again later, build a new DataFrame from the source tables.

oct_15_orders = spark.table("main.sales.orders").filter(F.col("order_date") == "2026-10-15")
```

### `df.storageLevel`

Gets the storage level of `df`.

* **Returns**: `StorageLevel.DISK_ONLY` while `df` is cached. `StorageLevel.NONE` before you cache it and after you call `df.unpersist()`.

* Python
* Scala

Python

```
from pyspark import StorageLevel

oct_15_orders.cache()

oct_15_orders.storageLevel == StorageLevel.DISK_ONLY  # True
```

Scala

```
import org.apache.spark.storage.StorageLevel

oct15Orders.cache()

oct15Orders.storageLevel == StorageLevel.DISK_ONLY // true
```

## Lifecycle and time limits

Cached data exists only within the Databricks session where you cache it. It becomes inaccessible when the session ends, and it lasts at most seven days. After the seven-day limit, using a cached DataFrame raises an error instead of reading the source tables again. To cache again, start a new session.

## Storage and cleanup

Databricks manages the storage for cached data automatically. Cached data is stored in cloud storage, with the specific storage location depending on your workspace type:

* **Serverless workspaces**: Cached data is stored in [default storage](/aws/en/storage/default-storage). If you have configured a customer-managed key for managed services, cached data uses that key. See [Customer-managed keys for encryption](/aws/en/security/keys/customer-managed-keys).

* **Classic workspaces**: Cached data is stored in the workspace storage bucket that is [configured at workspace creation time](/aws/en/admin/workspace/create-uc-workspace#storage). You can configure encryption at the storage bucket level.
