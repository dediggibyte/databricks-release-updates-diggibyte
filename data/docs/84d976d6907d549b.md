Beta

This feature is in [Beta](/aws/en/release-notes/release-types). To use it, a workspace admin must turn on **Lakebase Insights** from the **Previews** page. See [Manage Databricks previews](/aws/en/admin/workspace-settings/manage-previews).

Insights is a background agent that reviews a Lakebase project's telemetry from `system.lakebase` and surfaces issues and early warnings without you having to ask. It runs per project, in isolation, on a managed Databricks system identity, either on a schedule you set or once on demand. This page explains how to enable Insights for a project, then walks through a real insight end to end: what it found, why it matters, and how to respond.

Insights jobs scheduled through earlier observability configurations have stopped, and their schedules aren't migrated. Those configurations no longer write telemetry to their Unity Catalog destinations. Their dashboards retain historical data but receive no new data. To keep getting insights, turn on Insights and set an analysis frequency for each project in **Settings**. See [Lakebase telemetry in system tables](/aws/en/oltp/projects/observability-telemetry-reference).

Insights detects and diagnoses an issue. Resolving it is usually the next step, in [Genie](/aws/en/oltp/projects/lakebase-genie), which picks up the diagnosis and carries out a fix you confirm. You can also ask Genie about a problem directly, without waiting for an insight.

note

There's no separate charge for storing the captured telemetry within its 7-day retention period. Other costs are bundled into products you already use. Querying the telemetry counts toward the compute you run the query on. Each Insights run counts toward the compute and the model tokens it consumes in your account, so the analysis frequency you set determines how often that happens. Asking Genie counts toward your Genie usage.

## Prerequisites

* The **Lakebase Insights** preview must be enabled for your workspace. A workspace admin can enable it from the [Previews page](/aws/en/admin/workspace-settings/manage-previews).
* You need a Lakebase project on AWS or Azure, with a running compute.
* You need **CAN MANAGE** on the project to configure Insights and view its findings. See [Manage project permissions](/aws/en/oltp/projects/manage-project-permissions).

## Enable and use Insights

### Enable Insights for a project

To set up Insights, complete these steps:

1. If the **Lakebase Insights** preview isn't already enabled, ask a workspace admin to enable it from the [Previews page](/aws/en/admin/workspace-settings/manage-previews). Workspaces that used Insights before already have this preview; its former name was **Lakebase Advanced Postgres Telemetry**. Because Insights analyzes telemetry in `system.lakebase`, enabling this preview also enables **Lakebase Observability in System Tables** if that preview isn't already enabled.
2. For each project you want Insights to analyze, open **Settings**, enable Insights, and set its **analysis frequency**. Scheduled runs begin only after you configure that project.

The agent's analysis instructions aren't configurable.

### Find an insight

Insights evaluates telemetry on the schedule you set, so expect a delay between an issue occurring and an insight appearing for it, particularly on a newly configured project. You can also run the agent once, on demand, instead of waiting for the next scheduled run.

To see a project's insights, open the project, go to **Monitoring**, and select the **Insights** tab. Each row shows a **Severity** (for example Minor or Moderate), the **Insight** title, the **Time window** the issue covers, and its **Status**.

### Read an insight

Click an insight to open its detail page. Every insight follows the same structure:

* **Summary**: what's happening, in plain language.
* **Evidence**: the specific signals and values that support the diagnosis, in a table.
* **Recommendations**: concrete next steps, with the reasoning behind each one.

What Insights finds depends on your own telemetry, so your insights differ from the one below. This is a real insight, included to show the level of detail to expect.

In this example, "Idle session locked out 4 updates," the subtitle already tells you where to look: "Idle session held locks; UPDATE waits totalled 749 s." The Summary explains what happened: a session opened a transaction, went idle while still holding a row lock, and stayed that way for roughly 9.5 minutes until the database's own idle-in-transaction timeout forcibly closed it. The Evidence table backs that up with the specific numbers, including the terminating log entry and a total of 749 seconds of UPDATE wait time spread across 4 calls, averaging 187 seconds each for updates that would normally complete in milliseconds.

> **Recommendations:**
>
> 1. **Tune `idle_in_transaction_session_timeout` to a safe value**, such as 30-60 seconds, so an idle session releases its locks quickly instead of blocking other queries for minutes.
> 2. **Audit for unclosed transactions and use connection pooling with short checkout timeouts**, so a client that opens a transaction and goes idle can't hold a lock indefinitely.

The evidence identifies the session responsible, how long it held the lock, and the wait time it cost other queries. Severity is inferred from the available data, so read the Evidence to confirm the root cause before acting on Severity alone.

### Respond to an insight

After you've read an insight, respond in one of three ways:

* **Apply the recommendation yourself**, using the evidence and recommendations as a guide.
* **Click Fix with Genie** on the insight's detail page to hand it off to the interactive agent and keep investigating conversationally. This helps when the recommendation needs more context before you act, or when the fix involves a database-side change. See [Investigate and fix issues with Genie](/aws/en/oltp/projects/lakebase-genie).
* **Set its status** to **Resolved** once you've addressed it, or **Not an issue** if it doesn't need action.

## A finding can disappear on its own

Because Insights re-evaluates on its own schedule, a finding can drop off the list even if you never change its Status: a transient event like a one-time bulk load might not recur in a later window, or the compute behind it might scale to zero and resume fresh with the problematic session gone. A finding leaving the active list doesn't mean anyone marked it **Resolved** or **Not an issue**, or that anything went wrong. It reflects that the condition is no longer present in the latest evaluation window.
