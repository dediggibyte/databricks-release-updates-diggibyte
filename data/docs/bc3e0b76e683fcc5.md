Service policies let you govern the content of interactions with AI services registered in Unity Catalog, including external MCP servers and models from any provider, not just Databricks-hosted ones. Unity Catalog grants determine *whether* a principal can call a service. Service policies govern *how* that interaction proceeds, based on the content of the request and response and on who is making the call.

Service policies are the mechanisms you use to implement guardrails for AI services. If you're looking to add guardrails, such as blocking sensitive data, prompt injection, or unsafe content, service policies are the mechanism: Databricks has built-in guardrails for common risks, you can write custom policies for rules specific to your organization, and you can enforce a third-party guardrail vendor's decisions with an external service policy.

This matters most when agents act on behalf of users. An agent inherits everything the user can access, and services often reach external systems. Service policies let you set guardrails on that activity. For example, you can require user consent before an agent pushes code to a Git repository through an MCP Service, deny a model response that contains personally identifiable information (PII), or block unsafe content.

Custom policies can also check and enforce the presence or absence of caller-supplied request tags. See [Require an eligible project](/aws/en/data-governance/unity-catalog/service-policies/policy-examples#require-eligible-project) and the [request tags reference](/aws/en/data-governance/unity-catalog/service-policies/policy-function-reference#request-tags).

Service policies are one of three kinds of [attribute-based access control (ABAC) policy](/aws/en/data-governance/unity-catalog/abac/) in Unity Catalog:

* [ABAC GRANT policies](/aws/en/data-governance/unity-catalog/abac/grant-policies) grant Unity Catalog privileges on securables whose governed tags match a condition. They control whether a principal can reach an object.
* [Row filter and column mask policies](/aws/en/data-governance/unity-catalog/abac/policies) control which rows and columns a principal sees in a table.
* Service policies govern the content of each request and response to an AI service, to allow or deny it. On an MCP Service, a policy can also hold an input request for approval.

ABAC GRANT policies are access control. Row filter and column mask policies and service policies are *content* policies, which govern what happens after a principal has access. Like a row filter or column mask, a custom SQL service policy references a Unity Catalog function that contains the governance logic and attaches it to a securable.

## How service policies complement Unity Catalog grants

Unity Catalog privileges and service policies address different governance questions and operate at different enforcement points.

| **Aspect** | **Unity Catalog privileges** | **Service policies** |
| --- | --- | --- |
| Question answered | Can this principal call this service? | How must this interaction proceed? |
| Inputs | Principal identity and granted privileges | Request content, response content, request tags, tool annotations, and actor context |
| Enforcement point | Before the request reaches the service | Before the service is invoked (input phase, ON CALL) and after the service responds (output phase, ON RESULT) |
| Granularity | Per principal, per securable | Per request, based on content and context |

Service policies don't replace Unity Catalog grants. A principal must first have the appropriate Unity Catalog privileges to call a service. Service policies then evaluate the content of each interaction to enforce additional governance rules.

## Policy decisions

A service policy evaluates the content of a request or response and returns one of three outcomes:

* **ALLOW**: the interaction proceeds.
* **DENY**: the policy blocks the interaction. For [chat-style model APIs](#supported-model-apis), instead of an error status, Databricks returns a successful (HTTP 200) response. On a Model Service or Model Provider Service, the assistant turn carries a short message naming the service policy that blocked, and a top-level `databricks_service_policy` object carries the structured detail, including the block `reason`. Returning the block as a normal turn keeps conversational clients that resend the full history, such as coding agents, from re-triggering the same block on every later turn. An embedding input denial returns HTTP 400 and blocks the whole request before the model runs. On an MCP Service, the response is a JSON-RPC error with the block `reason` in `error.message`.
* **ASK**: on an MCP Service, the policy pauses a request for user approval before the tool runs. Use this action when a user must approve a sensitive operation, such as a destructive MCP tool call. For external agents calling an MCP Service, the approval prompt is delivered through MCP URL-mode elicitation. If a custom policy function returns `ASK` for a Model Service or Model Provider Service, Databricks blocks the request or response because these services cannot ask the user for approval. See [Return a decision](/aws/en/data-governance/unity-catalog/service-policies/create-service-policy#return-a-decision).

A custom policy is either a SQL user-defined function (UDF) that receives the interaction event (which includes the actor and the request or response content) and returns a decision result, or an LLM-as-a-judge policy that classifies the content against criteria you write in natural language. Built-in policies are managed by Databricks, and an [external service policy](#external-service-policies) sends the content to a third-party guardrail service that returns the decision.

A custom policy can also be a [Python UDF](/aws/en/data-governance/unity-catalog/service-policies/python-policies).

## Evaluation points

Databricks evaluates service policies at the following points for MCP tool calls and [supported model API requests](#supported-model-apis):

* Input (ON CALL): Before Databricks invokes the service, against the request. Use this phase to inspect requests before they reach the underlying service. For example, block a request that invokes a destructive MCP tool, or deny a prompt that contains sensitive data before it reaches a model.
* Output (ON RESULT): After the service responds, against the response. Use this phase to inspect responses before they return to the caller. For example, block a response that contains hallucinated content or sensitive data.

Embedding requests support the input phase only. No policy evaluates the resulting vectors.

On model services and model provider services, output policies can check a streaming response as it's generated and release approved text before the model finishes. See [Streaming responses](#streaming-responses).

For chat-style model APIs and MCP tool calls, a custom policy function runs at both points. It inspects the current phase (`event:type`) and decides how to act, so a single policy can govern the request, the response, or both. To act on only one phase, branch on `event:type` in the function body. For built-in policies and custom LLM-as-a-judge policies, you choose the phase in the policy form's **Phase** setting instead. Some built-in policies support different phases on different services. The Jailbreak guardrail runs only on the input phase on model and model provider services, and on input, output, or both on MCP services. The policy form preselects output for Jailbreak on an MCP service, but API callers must explicitly set the policy's `options.phases` request field to `pre_call` (input), `post_call` (output), or `pre_call,post_call` (both). Hallucination detection runs only on the output phase. External service policies are also scoped by phase: you choose the input phase, the output phase, or both when you attach one.

## Order of evaluation

You can attach more than one service policy to a service. Each attachment has a rank (priority), and a `DENY` at one rank stops evaluation at later ranks. Databricks evaluates ranks in ascending order on the input phase (ON CALL, lowest rank first) and in the reverse order on the output phase (ON RESULT). Policies at the same rank are evaluated in two stages, as described below. Use different ranks to control evaluation order.

### Evaluation within a rank

For chat-style model APIs and MCP tool calls, Databricks evaluates policies at the same rank in two stages:

1. Blocking LLM-as-a-judge policies run in parallel. These are the built-in and custom LLM-as-a-judge policies that block (`DENY`) content, such as unsafe-content detection. Because they are the model-backed checks, running them concurrently means their added latency is roughly that of the slowest single evaluation, not their sum.
2. The remaining policies then run sequentially, but only if no policy in the first stage returned `DENY`. This stage covers custom policy functions, external service policies, the `system.ai.detect_sensitive_data` built-in policy, and policies that pause for approval (`ASK`), including an LLM-as-a-judge policy set to ask instead of block. Their order within this stage is undefined. `ASK` pauses an input call only for MCP Services. For Model Services and Model Provider Services, `ASK` blocks the request or response.

A `DENY` in the parallel stage skips the sequential stage. The sequential stage doesn't stop at a `DENY`: every policy in it runs, even after one returns `DENY`. For example, a custom SQL policy that denies a request doesn't stop an external service policy at the same rank from sending the content to its vendor. A `DENY` in either stage stops evaluation at later ranks, so to skip a policy when another one denies, put the denying policy at a rank that's evaluated first.

For embedding requests, blocking judges at the same rank run one at a time, with up to four input items checked concurrently. A judge `DENY` skips the remaining policies at that rank. See [Embedding input guardrails](#embedding-input-guardrails) for the effect on judge calls and latency.

## Streaming responses (Beta)

Beta

Streaming evaluation is in [Beta](/aws/en/release-notes/release-types). It's part of the **Unity Gateway Service Policies** preview and has no separate toggle. See  [Manage workspace-level previews](/aws/en/admin/workspace-settings/manage-previews#workspace).

On model services and model provider services, each policy has a **Response evaluation** setting that controls how output policies handle streaming requests:

* **Streaming evaluation**: The default. Output policies check the response as the model generates it, and Databricks releases approved text before the model finishes.
* **Full response evaluation**: Output policies evaluate the complete response before any of it is released.

Existing policies also use streaming evaluation by default. Select **Full response evaluation** when no text can reach the client before the whole response passes, or when a custom policy requires the complete answer or final fields such as token usage.

If any output policy that applies to a request uses full response evaluation, including a policy in **Log** mode, every output policy evaluates the complete response. For chat-style requests, custom SQL and Python policies run on both phases, so their setting also counts. With streaming evaluation, those functions run on each window even if their logic only acts on the request. The setting has no effect on input-only policies.

Streaming evaluation applies to streaming requests to the [supported chat-style model APIs](#supported-model-apis). Output policies use full response evaluation for non-streaming chat-style requests and MCP tool results. In the API, set a policy's `stream_mode` field to `STREAM_MODE_WINDOWED_SYNC` for streaming evaluation or `STREAM_MODE_FULLY_BUFFERED` for full response evaluation. Omitting the field selects streaming evaluation. MCP services reject the field.

### How streaming evaluation works

With streaming evaluation, Databricks holds the model's output and checks it in overlapping windows:

1. With the default settings, Databricks runs the output policies after a few hundred new characters arrive. If the stream is slower, the next chunk after about a second can also trigger a check. Only one check runs at a time per request.
2. Each check rereads recent response text, typically the last 16,000 characters, and all unreleased text if that's longer. The overlap gives policies context from earlier windows, rather than only the newest text.
