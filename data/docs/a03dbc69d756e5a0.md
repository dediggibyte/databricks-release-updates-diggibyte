Consumer access is a workspace entitlement that gives users access to workspace-level Genie One and Lakeflow Designer. When users with consumer access sign in, they are directed to Genie One instead of the standard Databricks workspace, where they can discover and interact with dashboards, Genie Agents, and Databricks Apps shared with them. Account-level Genie One is available to all Databricks account users and does not require this entitlement. See [Account-level Genie One](/aws/en/genie-one/enable-genie-one#account-level).

This page explains how workspace admins can grant consumer access, outlines the capabilities and restrictions for users with this entitlement, and describes relevant data governance controls.

## Consumer access capabilities

Consumer access is a [workspace entitlement](/aws/en/security/auth/entitlements) that workspace admins can assign to individual users or user groups. It adds business users to the workspace under a unified permissions model, giving them access to Lakeflow Designer and a simplified experience for discovering and working with the dashboards, Genie Agents, Databricks Apps, and other accessible workspace resources. Existing access control lists (ACLs) govern that access, so consumers work only with the resources they're already permitted to use. Because entitlements are additive, users with additional workspace entitlements can use both the simplified consumer experience and standard workspace interfaces. After you migrate a workspace to the new system group behavior, you select each principal's entitlements when you add them, so you can add consumer-only users without granting **Workspace access** or **Databricks SQL access**. See [Migrate workspace entitlement control](/aws/en/security/auth/system-group-entitlements-migration).

Users with only the consumer access entitlement receive:

* Access to Genie One, a simplified workspace interface for working with dashboards, Genie Agents, and Databricks Apps shared with them. A Genie Agent that calls a Unity Catalog function using an [HTTP connection](/aws/en/query-federation/http) also requires the **Workspace access** entitlement. Users with only consumer access receive a permission error when the agent runs that function.
* Access to Lakeflow Designer.
* Access to Unity Gateway services shared with them. Using the Unity Gateway CLI (`ug`) or the REST API, consumer access users can:
  + List model services and query Databricks-hosted foundation models.
  + List model provider services and query registered external providers.
  + List MCP services and call the MCP tools shared with them. The `system.ai.web_search` and `system.ai.sandbox` built-in MCP services aren't available to consumer access users.
  + List and download shared skills.
  + Read and apply an admin-published coding agent configuration.
  + Send client-side traces from their coding agent to the unified trace table, if an admin turns on tracing in the coding agent configuration. See [Enable client-side tracing](/aws/en/ai-gateway/coding-agent-observability#client-side-tracing).
  + Check their own spend against their coding agent budget with `ug usage`.
* Membership in the workspace’s users system group, displayed as the `users` group in the UI.
* Eligibility to be granted access to SQL warehouses for use with third-party BI tools, such as Power BI and Tableau. However, consumer access users cannot view SQL warehouses or **Query History**, even if permissions on compute and data have been granted.

### Workspace resources

This feature is in [Beta](/aws/en/release-notes/release-types).

Users with consumer access can read and write existing workspace resources and create new resources where their permissions allow. Databricks curates which workspace services are available in the consumer experience. Products such as Genie One and Lakeflow Designer use this access to run richer analyses (for example, forecasting) and to create certain asset types (for example, slides). Existing ACLs continue to govern what each user can open, run, or save, and consumer access doesn't grant any additional permissions.

note

Because consumer access relies on existing permissions, review the permissions granted to the `users` group, compute, service principals, and jobs. See [Permission best practices for consumer access](#permission-best-practices).

important

Until your workspace migrates to the new entitlement behavior, users with consumer access also inherit all entitlements granted to the `users` system group. If that group grants elevated privileges such as workspace access or Databricks SQL access, consumer users receive those privileges too. When you migrate, Databricks automatically moves those entitlements to a new group and you select each principal's entitlements individually going forward. This change is enforced for all workspaces on September 14, 2026. See [Migrate workspace entitlement control](/aws/en/security/auth/system-group-entitlements-migration).

To grant consumer access to an individual user, assign the **consumer access** entitlement in workspace settings. See [Manage entitlements](/aws/en/security/auth/entitlements). To add consumer access users at scale, sync groups from your identity provider using automatic identity management. See [Automatic identity management](/aws/en/admin/users-groups/automatic-identity-management/).

## Permission best practices for consumer access

Consumer access doesn't grant permissions on workspace objects, compute, or data. Existing permissions determine what users and service principals with consumer access can use; the same permission model applies to both. Databricks recommends reviewing the following permissions, which affect all workspace users:

* **Grant permissions to the `users` group sparingly**: Every user and service principal with consumer access belongs to the workspace `users` group and inherits its permissions. Review the group's permissions on workspace objects, compute, SQL warehouses, and service principals. Grant a permission to this group only if every principal in the workspace needs it. See [Groups](/aws/en/admin/users-groups/groups).
* **Keep sensitive objects out of the workspace Shared folder**: Every workspace user and service principal has full permissions on objects stored in **Shared**, including principals with only consumer access. Store sensitive objects elsewhere, including notebooks used by jobs that run as another identity. Use folders for which the `users` group has no permissions. See [Special folders](/aws/en/workspace/workspace-browser#special-folders).
* **Grant compute permissions only to groups that need them**: Users and service principals with consumer access can run code on any compute they are permitted to use: serverless compute, classic compute with the CAN ATTACH TO permission, and SQL warehouses with the CAN USE permission. They can access that compute from the consumer experience or from external tools such as Databricks Connect. See [Compute ACLs](/aws/en/security/auth/access-control/#clusters) and [SQL warehouse ACLs](/aws/en/security/auth/access-control/#sql-warehouses).
* **Don't grant the Service Principal User role to the `users` group**: Anyone with the **Service Principal User** role on a service principal can run jobs as that service principal. This includes users with only consumer access. Grant the role only to users and groups that need it. See [Roles for managing service principals](/aws/en/security/auth/access-control/service-principal-acl).
* **Limit who can edit jobs**: The CAN MANAGE and IS OWNER permissions let a user modify a job's tasks. Because the job continues to run as its **Run as** identity, these permissions effectively let the user run code as that identity. Review these permissions on jobs that run as a service principal or workspace admin, and grant them only to users you trust to run code as that identity. The same restriction applies to edit permissions on the notebooks and files that the job runs. See [Manage identities, permissions, and privileges for Lakeflow Jobs](/aws/en/jobs/privileges).

note

If workspace visibility control is disabled, every workspace user, including users with consumer access, can see the names of notebooks, files, and folders even when they can't open those objects.

## Data governance

Consumer access users are members of the workspace and work within the unified data access controls you've set up using Unity Catalog. They can view and run dashboards, Genie Agents, and Databricks Apps shared with them directly or shared with a group they belong to. If the sharing user has selected the option to run queries using the viewer's credentials, the viewer's own Unity Catalog privileges apply, and they see only the data they're authorized to access. They can also be assigned permissions to use Unity Catalog-governed data in third-party BI tools.

Every Genie One interaction respects Unity Catalog permissions. When users connect external knowledge sources such as Google Drive or SharePoint, Genie One honors those sources' permissions as well.
