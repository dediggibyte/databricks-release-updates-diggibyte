This page teaches you how to create and configure notification destinations for your workspace.

System notifications are messages that tell you when your workflow experiences a run event (start, success, and failure). By default, notifications are sent to user email addresses, but admins can configure alternate notification destinations using webhooks or the [Databricks Genie app for Slack and Microsoft Teams (Public Preview)](#databricks-app-destinations). This allows you to build event-driven integrations with Databricks.

Admins can also configure notification destinations to receive access requests from workspace users, such as privilege requests on Unity Catalog objects.

You must be a Databricks workspace admin to manage notification destinations. After a destination is configured, it is available to all users.

Account-level events, such as budget alerts, use account-level notification destinations, which account admins configure in the account console. See [Manage account-level notification destinations](/aws/en/admin/account-settings/notification-destinations).

## Networking requirements

For webhook-based destinations, the receiving endpoint must meet the following requirements:

* Databricks enforces the use of HTTPS for security. The notification destination must use Secure Sockets Layer (SSL) certificates signed by a trusted certificate authority.
* The notification destination must add both the workspace control plane and data plane outbound IP addresses to its allowlist:
  + For control plane webapp IP addresses, see [IP addresses and domains for Databricks services and assets](/aws/en/resources/ip-domain-region).
  + For data plane outbound IP addresses, see the [`ip-ranges.json`](https://www.databricks.com/networking/v1/ip-ranges.json) file that Databricks publishes. Search the file for your workspace's data plane region and allowlist the corresponding outbound IP addresses in your networking stack.

    Databricks may update the outbound IPs as often as once every 30 days. Updated IPs become active as soon as 60 days after publication, so review the file regularly and update your allowlist before the activation window closes.

    To track changes between releases, save successive versions of the JSON file and compare the `timestampSeconds` value. Filter entries where:

    - The `service` field is `Databricks`
    - The `platform` field is `aws`
    - The `type` field is `outbound`

## Create a new notification destination

To configure a new notification destination

1. Click your username in the top bar of the workspace and select **Settings** from the dropdown.
2. In the **Workspace admin** section, click the **Notifications** tab.
3. Click the **Manage** button.
4. Click **+Add destination**.
5. Select a destination type. The following destinations are currently supported:
   * Email
   * [Slack](#slack-destination)
   * Webhook, with optional [OAuth authentication (Beta)](#oauth-webhook-destinations)
   * Microsoft Teams
   * [PagerDuty](#pagerduty-destination)
   * [AWS EventBridge (Beta)](#eventbridge-destination)
   * [ServiceNow (Beta)](#servicenow-destination)
   * [Asana (Beta)](#asana-destination)
6. Configure the destination based on the type.
7. Click **Create**.

## Webhook payloads

The service that sends a notification defines the webhook payload. For the payloads that jobs send, see [HTTP webhook payloads](/aws/en/jobs/notifications#webhook-payloads). For the payload that Databricks SQL alerts send after a state change, see [SQL alert webhook payload](/aws/en/sql/user/alerts/webhook-payload).

## Use different credentials for each destination

The configuration of a destination is securely stored encrypted in your Databricks workspace. For destinations that require you to provide a URL or credentials, Databricks recommends using different credentials for each configured destination. This limits the impact if a third-party endpoint is compromised. These include:

* Slack using a webhook: the URL to which the notification is sent.
* Microsoft Teams using a webhook: the URL to which the notification is sent.
* PagerDuty: integration key used to uniquely route notifications to a PagerDuty service.
* Webhook: a username and password for HTTP Basic authentication, or a client ID and client secret for [OAuth authentication (Beta)](#oauth-webhook-destinations).
* Asana: personal access token.

Using different secrets for each configured destination allows you to individually revoke access of individual notification destinations without impacting the operation of all other destinations in your Databricks workspace.

## OAuth authentication for webhook destinations

Beta

This feature is in [Beta](/aws/en/release-notes/release-types). To use it, a workspace admin must turn on **Destination Type Generic Webhook Oauth** from the **Previews** page. See  [Manage workspace-level previews](/aws/en/admin/workspace-settings/manage-previews#workspace).

Use OAuth 2.0 client credentials to send notifications to an endpoint that requires an access token. Databricks obtains the token from your identity provider and uses it to authenticate the notification request.

Your identity provider must support the client credentials grant. Both the receiving endpoint and the token endpoint must use HTTPS.

To create an OAuth webhook destination:

1. In **Settings** > **Notifications**, click **Manage**, then **+Add destination**.
2. Enter a name and select **Webhook** for **Type**.
3. For **Authentication mode**, select **OAuth**.
4. Enter the following values:
   * **URL**: The endpoint that receives notifications.
   * **Client ID** and **Client secret**: The credentials issued by your identity provider.
   * **Token endpoint URL**: The endpoint from which Databricks obtains an access token.
   * **Scopes** and **Audience**: Enter these optional values if required by your identity provider. Separate multiple scopes with commas.
5. Click **Create**.

The client ID, client secret, and token endpoint URL are required together. OAuth cannot be combined with HTTP Basic authentication.

To verify the configuration, open the destination's three-dot menu and click **Test**. Databricks obtains an access token and sends a sample notification. If the test fails, check the credentials, scopes, audience, receiver permissions, and network access to both endpoints.

### Compliance availability for OAuth webhook destinations

For workspaces with the [compliance security profile](/aws/en/security/privacy/security-profile) enabled, region eligibility depends on the selected compliance standards. For region names, see [supported regions](/aws/en/resources/supported-regions).

* If one or more standards are selected, open each standard's page from the [compliance security profile overview](/aws/en/security/privacy/security-profile#compliance-security-profile-overview). Find "Destination Type Generic Webhook Oauth" in its regional support table. Your workspace region must be listed for the feature under every selected standard.
* If no compliance standard is selected, no additional standard-specific region restriction applies. Check the workspace's [Previews page](/aws/en/admin/workspace-settings/manage-previews#workspace) for **Destination Type Generic Webhook Oauth**.

## AWS EventBridge destination

Beta

This feature is in [Beta](/aws/en/release-notes/release-types). To use it, a workspace admin must turn on **Destination Type Aws Eventbridge** from the **Previews** page. See  [Manage workspace-level previews](/aws/en/admin/workspace-settings/manage-previews#workspace).

Workspaces hosted on any supported cloud can send notifications to an Amazon EventBridge event bus in your AWS account. An EventBridge rule routes matching notifications to a target, such as an AWS Lambda function. Notification data leaves Databricks when you send it to EventBridge.

### EventBridge requirements

EventBridge setup requires workspace admin access and permission to create or configure the following resources in your AWS account:

* An EventBridge event bus in the region that receives notifications.
* An AWS Identity and Access Management (IAM) role in the same AWS account as the event bus.
* An EventBridge rule and a target that consumes the notifications.

You also need the AWS CLI configured with credentials that have `iam:GetRole` permission in that AWS account.

Contact your Databricks account team to get the CloudFormation template that creates the IAM role.

The event bus and role must use the commercial AWS partition (`arn:aws:`). The region in the event bus Amazon Resource Name (ARN) determines where Databricks sends events.

### Create an EventBridge destination

1. [Create an event bus](https://docs.aws.amazon.com/eventbridge/latest/userguide/eb-create-event-bus.html), or select an existing bus, and copy its ARN.
2. In Databricks, go to **Settings** > **Notifications**, click **Manage**, then **+Add destination**.
3. Enter a name and select **AWS EventBridge** for **Type**.
4. Copy the **Databricks principal ARN** and **External ID** displayed in the form.
5. In the AWS account that owns the event bus, open AWS CloudFormation and create a stack from the template that your account team provided. Enter the following template parameters:

   * `DatabricksPrincipalArn`: The principal ARN copied from the destination form.
   * `ExternalId`: The External ID copied from the destination form.
   * `EventBusArn`: The exact event bus ARN. Don't use wildcards.

   Keep the template's trust and permissions policies unchanged. Acknowledge that the stack creates IAM resources, then create the stack. The role grants only `events:PutEvents` on the specified bus.
6. Copy `RoleArn` from the stack outputs. Run the following command, replacing `<role-name>` with the final component of that ARN, and send the output to your account team to confirm the trust policy and External ID:

   Bash

   ```
   aws iam get-role --role-name <role-name> --output json
   ```
7. After your account team confirms the configuration, return to the destination form and enter the **Event bus ARN** and **Role ARN**. Click **Create**.

The destination appears in the notification destinations list.

Click the destination name to edit its settings, or select **Delete** from its three-dot menu to remove it. Deleting the destination in Databricks doesn't delete the CloudFormation stack, IAM role, or event bus in your AWS account. Delete those resources separately in AWS if you no longer need them.

The External ID is your Databricks account ID, shared by the workspaces in that account. It isn't a secret. Any workspace admin in the same Databricks account who knows the role and bus ARNs can create a destination that sends to this bus. EventBridge rule filters control which events reach a target. They don't restrict which workspaces can send to the bus.

Databricks uses AWS Security Token Service (STS) to obtain temporary credentials for this role. You don't provide AWS access keys to Databricks.

### Route EventBridge notifications to a target

Each EventBridge event has `source` set to `databricks.notifications`, a `detail-type` identifying the notification type, and `detail` containing the notification payload. The `detail.workspace.id` field identifies the sending workspace across supported notification types.

1. [Create an EventBridge rule](https://docs.aws.amazon.com/eventbridge/latest/userguide/eb-create-rule.html) on the event bus you configured.
2. Set the event pattern to match the notifications you want to receive. For example, this pattern matches `JOB_RUN_ERROR_V2` notifications from one workspace. Replace `<workspace-id>` with your workspace ID:

   JSON

   ```
   {

   "source": ["databricks.notifications"],

   "detail-type": ["JOB_RUN_ERROR_V2"],

   "detail": {

   "workspace": {

   "id": ["<workspace-id>"]

   }

   }

   }
   ```

   To route all notification types for that workspace, omit `detail-type` from the pattern.
3. Select the rule's target, configure its required permissions, and enable the rule.

EventBridge uses the rule to route matching events to the target. Delivery can produce duplicate notifications. The payload varies by notification type, and the destination doesn't supply a shared deduplication key. For `JOB_RUN_ERROR_V2`, a target can use `detail.workspace.id`, `detail.run.run_id`, `detail.run.attempt`, and `detail-type` together to identify repeated notifications.

## Slack destination

To set up a webhook-based Slack destination, follow the instructions in [Incoming webhooks for Slack](https://api.slack.com/messaging/webhooks). Paste the generated URL into your Databricks notification destination. To use the Databricks Genie app instead, see [Slack and Microsoft Teams Genie app destinations](#databricks-app-destinations).

## Slack and Microsoft Teams Genie app destinations

Preview

This feature is in [Public Preview](/aws/en/release-notes/release-types). To use it, a workspace admin must turn on **Destination Type Databricks App Slack** or **Destination Type Databricks App Teams** from the **Previews** page. See  [Manage workspace-level previews](/aws/en/admin/workspace-settings/manage-previews#workspace).

Use the Databricks Genie app to connect your Slack workspace or Microsoft Teams tenant to your Databricks workspace. Then select an available channel as a notification destination.

You can use Genie app destinations with the following features:

* [SQL alerts](/aws/en/sql/user/alerts/create): Slack and Microsoft Teams.
* [Unity Catalog access requests](/aws/en/data-governance/unity-catalog/manage-privileges/access-request-destinations): Slack and Microsoft Teams.
* Model Serving endpoint notifications: Slack.
